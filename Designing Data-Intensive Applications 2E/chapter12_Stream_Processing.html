스트림 처리

배치 처리는 입력이 끝나 있다고 가정합니다. 그러나 현실의 데이터는 끝나지 않습니다. 사용자는 계속 클릭하고, 센서는 계속 값을 보냅니다. 끝나지 않는 입력을 계속 처리하는 방식이 스트림 처리입니다.

"데이터는 멈춰 있는 사실이 아니라, 흘러가는 사건의 연속이다." — 12장을 지배하는 관점의 전환

도입 배치에서 스트림으로

배치의 전제: "입력은 이미 끝나 있다"

배치 처리는 유한한(bounded) 입력을 전제합니다. 파일 크기를 알 수 있고, 언제 다 읽었는지 알 수 있고, 그래서 정렬하고 다시 실행할 수 있습니다. 이 확실성이 배치의 강력함이었습니다.

하지만 실제 데이터는 대부분 무한(unbounded)합니다. 어제 자정에 끊어서 하루치를 돌리는 방식은, 결과가 최대 하루 늦다는 뜻이기도 합니다.

지연을 줄이려면 처리 주기를 짧게 잘라야 하고, 계속 잘게 자르다 보면 결국 이런 질문에 도달합니다 — "왜 굳이 자르는가?"

배치

유한 입력

끝이 있음 · 정렬 가능 · 재실행 쉬움 · 지연 큼

무한 입력

끝이 없음 · 도착 순서 제각각 · 지연 작음 · "완료"를 스스로 정의해야 함

이 장의 핵심 질문은 하나로 압축됩니다 — 끝나지 않는 데이터에서, 어떻게 "정확한 답"을 정의하고 지킬 것인가?
개념 이벤트 · 스트림

스트림의 기본 단위는 "이벤트"다

이벤트 event

어떤 시점에 일어난 일을 담은 작고 불변인 레코드입니다. 보통 발생 시각(타임스탬프)을 포함합니다.

예: 페이지 조회, 장바구니 담기, 온도 측정값, 결제 완료

생산자와 소비자

이벤트를 만드는 쪽이 생산자(producer), 받아 처리하는 쪽이 소비자(consumer)입니다.

관련된 이벤트를 묶은 단위를 토픽(topic) 또는 스트림이라 부릅니다.

배치와의 대응

배치의 레코드 ↔ 스트림의 이벤트
배치의 파일 ↔ 스트림의 토픽

개념은 같고, 다른 것은 "끝"이 있는지입니다.

이벤트를 파일이나 DB에 쌓고 소비자가 주기적으로 폴링(polling)하게 만들 수도 있습니다. 하지만 지연을 줄이려 폴링을 자주 할수록, "새 것 없음"이라는 헛된 응답의 비용이 커집니다. 그래서 "새 이벤트가 생기면 알려주는" 전용 장치가 필요해집니다.

이벤트 스트림 전송

생산자가 만든 이벤트를 소비자에게 어떻게 잃지 않고, 순서를 지키며 전달할 것인가. 그리고 소비자가 느릴 때 무엇을 포기할 것인가.

12.1 메시징 시스템의 선택 기준

메시징 시스템은 두 질문으로 갈린다

질문 1

생산자가 소비자보다 빠르면?

  • 버린다(drop) — 최신 값만 중요할 때
  • 큐에 쌓는다(buffer) — 큐가 무한하지 않다는 사실이 문제
  • 배압(backpressure) — 생산자를 느리게 만든다
질문 2

노드가 죽거나 끊기면?

메시지를 디스크에 쓰거나 복제하면 잃지 않지만 비용이 듭니다. 반대로 손실을 허용하면 처리량과 지연이 좋아집니다.

"손실 허용"이 괜찮은지는 용도에 달려 있습니다. 지표 집계에서 몇 건 유실은 견딜 수 있지만, 결제 이벤트에서는 재앙입니다.

이 두 질문의 답이 곧 브로커 없는 직접 전달과 메시지 브로커, 그리고 전통 큐와 로그 기반 큐의 갈림길입니다.
12.1 브로커 없는 직접 전달

생산자가 소비자에게 바로 보내기

  • UDP 멀티캐스트 — 금융 시세처럼 낮은 지연이 절대적일 때. 애플리케이션이 직접 손실을 복구해야 합니다.
  • 브로커 없는 메시징 라이브러리 — ZeroMQ 계열. TCP·IP 멀티캐스트 위에 발행/구독을 얹습니다.
  • UDP 기반 지표 수집 — StatsD 계열. 손실을 전제로 하며, 집계값은 근사치가 됩니다.
  • HTTP/RPC 직접 호출 — 웹훅(webhook)처럼 소비자의 엔드포인트를 직접 호출합니다.
대가

직접 전달은 생산자와 소비자가 동시에 살아 있어야 동작합니다.

소비자가 죽어 있으면 그 사이의 메시지는 그냥 사라집니다. 재시도를 해도 생산자 쪽 메모리에 남아 있던 것만 재시도할 수 있고, 생산자까지 죽으면 그것마저 잃습니다.

즉 "손실 없음"의 책임 전부가 애플리케이션 코드로 넘어옵니다.

12.1 메시지 브로커

중간에 "버텨주는 서버"를 둔다

메시지 브로커(= 메시지 큐)는 생산자와 소비자 사이에 놓인, 메시지 전달에 특화된 데이터베이스입니다. 양쪽 모두 브로커에만 연결합니다.

덕분에 얻는 것:

  • 비동기 결합 해제 — 소비자가 죽어 있어도 생산자는 계속 보낼 수 있습니다.
  • 내구성 선택 — 큐를 디스크에 쓰거나 복제하도록 설정할 수 있습니다.
  • 부하 흡수 — 소비자가 느리면 큐가 길어지며 버텨줍니다.
DB와의 차이
  • DB는 명시적으로 지울 때까지 영구 보관, 전통 브로커는 전달되면 삭제합니다.
  • 따라서 브로커는 작업 집합이 작다고 가정합니다. 큐가 길어지면 처리량이 떨어질 수 있습니다.
  • DB는 인덱스·질의를 지원하고, 브로커는 패턴에 맞는 토픽 구독을 지원합니다.
  • DB는 질의할 때 결과가 나오고, 브로커는 데이터가 바뀌면 알려줍니다.
12.1 여러 소비자에게 전달하는 두 방식

같은 토픽, 정반대의 두 목적

로드 밸런싱 shared queue

각 메시지를 소비자 한 명에게만 줍니다. 여러 소비자가 일을 나눠 갖는 구조로, 처리 비용이 큰 작업을 병렬화할 때 씁니다.

소비자를 늘리면 처리량이 늘어납니다.

팬아웃 fan-out

각 메시지를 모든 소비자에게 보냅니다. 서로 독립적인 여러 소비자가 같은 이벤트를 각자 자기 목적으로 처리합니다.

배치에서 같은 파일을 여러 잡이 읽는 것과 같은 그림입니다.

둘은 함께 쓸 수 있습니다. "소비자 그룹"을 여러 개 두고(팬아웃), 각 그룹 안에서는 여러 인스턴스가 일을 나누는(로드 밸런싱) 조합이 실무의 기본형입니다.
12.1 확인응답과 재전달

"처리했다"는 신호가 없으면 다시 보낸다

소비자는 언제든 죽을 수 있습니다. 그래서 브로커는 소비자가 확인응답(ack)을 보낼 때까지 메시지를 지우지 않고, ack이 없으면 다른 소비자에게 재전달합니다.

여기서 익숙한 문제가 다시 등장합니다 — 소비자가 처리는 끝냈는데 ack만 잃어버린 경우입니다. 브로커는 구분할 수 없으므로 다시 보내고, 결과적으로 같은 메시지가 두 번 처리됩니다.

그래서 멱등성(idempotence) 또는 중복 제거 장치가 필요합니다.

더 고약한 부작용

로드 밸런싱 + 재전달이 만나면 순서가 깨집니다.

소비자 A가 메시지 m3을 처리하다 죽고, 그 사이 소비자 B가 m4를 먼저 끝내면, m3은 m4 뒤에 재전달됩니다.

브로커가 큐 안에서는 순서를 지켰더라도, 소비자가 보는 순서는 뒤바뀝니다. 메시지 사이에 인과관계가 있다면 치명적입니다.

회피법은 메시지별 큐 분리(=병렬성 포기)입니다. 여기서 로그 기반 브로커의 동기가 나옵니다.

12.1 두 종류의 브로커

지우는 큐 vs 남기는 로그

전통(AMQP/JMS 계열)

  • 전달·ack이 끝나면 삭제
  • 읽은 메시지를 다시 읽을 수 없음
  • 병렬 소비 시 순서 보장 약함
  • 메시지별 처리 비용이 크고 순서가 중요하지 않은 작업 큐에 적합

로그 기반

  • 추가 전용(append-only) 로그에 계속 쌓아둠
  • 소비해도 지우지 않음 → 재생 가능
  • 파티션 내부에서는 순서 보장
  • 이벤트 수가 많고 처리가 빠르며 순서가 중요한 스트림에 적합

Kafka, Kinesis, Pulsar 등이 이 계열입니다.

로그 기반 브로커는 DB의 복제 로그와 로그 구조 저장 엔진에서 이미 검증된 아이디어를 메시징에 그대로 가져온 것입니다.
12.1 로그 기반 브로커의 작동

파티션 · 오프셋 · 소비자 그룹

추가 전용 로그와 두 소비자 그룹

각 소비자 그룹은 자기 오프셋만 관리합니다. 그래서 한 그룹이 뒤처져도 다른 그룹은 영향을 받지 않고, 오프셋을 되돌리면 과거를 다시 읽을 수 있습니다.

12.1 순서와 처리량의 교환

순서는 파티션 단위로만 보장된다

파티션으로 확장

로그를 여러 파티션으로 나눠 다른 장비에 배치합니다. 파티션마다 독립적으로 읽고 쓰므로 단일 장비의 한계를 넘습니다.

파티션 내부 순서

같은 파티션 안에서는 쓴 순서 = 읽는 순서입니다. 오프셋이 단조 증가하는 시퀀스 번호 역할을 합니다.

파티션 사이의 순서는 보장되지 않습니다.

대가

순서를 지키려면 파티션 하나를 그룹 내 한 노드만 읽어야 합니다. 따라서 소비자 수 ≤ 파티션 수입니다.

느린 메시지 하나가 뒤의 모든 메시지를 막는 선두 차단(head-of-line blocking)도 생깁니다.

정리하면 — 메시지 처리가 느리고 순서가 상관없다면 전통 큐(메시지 단위 병렬화)가, 빠르고 순서가 중요하다면 로그 기반(파티션 단위 병렬화)이 맞습니다.
12.1 소비자 오프셋

메시지마다 ack하지 않고, 위치 하나만 기록한다

오프셋 N까지 처리했다는 사실을 기록하면, 그보다 앞선 모든 메시지를 처리했다는 뜻이 됩니다. 메시지마다 확인응답을 주고받을 필요가 없으니 추적 부담이 훨씬 작고 처리량이 높습니다.

이 구조는 단일 리더 복제의 로그 시퀀스 번호와 정확히 같습니다. 브로커가 리더, 소비자가 팔로워인 셈입니다.

소비자가 죽으면, 그룹의 다른 노드가 마지막으로 기록된 오프셋부터 다시 시작합니다.

여기서 생기는 중복

오프셋 기록은 처리보다 늦게 일어날 수 있습니다.

소비자가 오프셋 7까지 처리했지만 기록은 4까지만 되어 있는 상태에서 죽으면, 새 소비자는 5,6,7을 다시 처리합니다.

즉 로그 기반 브로커도 중복 처리를 피할 수 없습니다. 뒤에서 다루는 멱등성이 다시 필요해지는 지점입니다.

12.1 디스크 공간과 재생

로그는 결국 유한한 원형 버퍼다

계속 쌓기만 하면 디스크가 찹니다. 그래서 로그를 세그먼트로 나누고 오래된 세그먼트를 삭제하거나 보관 저장소로 옮깁니다. 사실상 크기가 큰 원형 버퍼(circular buffer)입니다.

여기서 위험한 시나리오가 하나 생깁니다 — 소비자가 너무 뒤처져서, 아직 읽지 않은 위치가 이미 삭제된 경우입니다. 그러면 그 메시지들은 조용히 사라집니다.

그래서 운영 지표로 소비자 지연(lag)을 반드시 감시하고, 지연이 커지면 경고를 받아야 합니다.

대신 얻는 큰 이점

느린 소비자는 남을 방해하지 않습니다. 버퍼가 브로커의 디스크이므로, 소비자가 뒤처져도 다른 소비자나 생산자는 영향받지 않습니다.

과거를 다시 읽을 수 있습니다. 오프셋만 되돌리면 됩니다. 소비 행위 자체가 로그를 바꾸지 않기 때문입니다.

코드를 고쳐 어제 데이터를 다시 처리하고 결과를 비교하는, 배치식 실험을 스트림에서도 할 수 있게 됩니다. 이 성질이 다음 절 전체의 토대입니다.

12.2

데이터베이스와 스트림

데이터베이스에 대한 모든 쓰기는 그 자체로 이벤트입니다. 이 관점을 받아들이면, 여러 시스템을 동기화하는 오래된 골칫거리가 스트림 문제로 바뀝니다.

이종 시스템 동기화이중 쓰기의 함정변경 데이터 캡처이벤트 소싱불변성의 힘과 한계
12.2 시스템 동기화 유지

같은 데이터가 여러 곳에 복사되어 있다

실제 시스템은 하나의 저장소로 끝나지 않습니다. OLTP 데이터베이스, 전문 검색 인덱스, 분석용 웨어하우스, 여러 겹의 캐시가 같은 데이터의 서로 다른 표현을 갖고 있습니다.

데이터가 바뀌면 이 모든 곳이 함께 바뀌어야 합니다. 배치 ETL로 주기적으로 전체를 덮어쓰는 방법이 있지만, 지연이 큽니다.

대안으로 흔히 쓰이는 것이 애플리케이션이 각 저장소에 직접 쓰는 이중 쓰기(dual write)입니다. 그리고 이것은 거의 항상 조용히 망가집니다.

관점의 전환

복사본 중 하나를 진실의 원천(source of truth)으로 정하고, 나머지를 모두 그로부터 파생된 뷰로 본다면?

그러면 필요한 것은 단 하나 — 원천의 변경을 순서대로 흘려보내는 스트림입니다.

12.2 이중 쓰기가 깨지는 방식

두 곳에 직접 쓰면, 두 곳의 결론이 달라진다

이중 쓰기 — 두 클라이언트의 경쟁

이중 쓰기는 경쟁 조건과 부분 실패라는 두 가지 결함을 동시에 갖습니다. 원자적 커밋으로 후자는 막을 수 있지만, 그러려면 이종 시스템에 걸친 분산 트랜잭션이 필요합니다.

12.2 변경 데이터 캡처 CDC

DB의 변경을 관찰해 스트림으로 만든다

변경 데이터 캡처는 데이터베이스에 기록된 모든 변경을 관찰해, 다른 시스템이 같은 순서로 적용할 수 있는 형태로 뽑아내는 것입니다.

구도는 명확합니다 — 원본 DB가 리더, 검색 인덱스·웨어하우스·캐시는 팔로워입니다. 로그 기반 브로커가 이 변경 로그를 나르기에 딱 맞습니다. 순서를 지키기 때문입니다.

DB의 복제 로그는 원래 내부용이라 공개된 API가 아닌 경우가 많았고, 그래서 CDC 도구들이 각 DB의 로그 형식을 해석하는 일을 맡습니다.

구현 방식
  • 트리거 기반 — 변경 시 별도 테이블에 기록. 구현은 쉽지만 오버헤드가 크고 깨지기 쉽습니다.
  • 복제 로그 파싱 — DB가 이미 쓰는 로그를 읽습니다. 스키마 변경 대응이 까다롭지만 훨씬 견고합니다.

MySQL의 binlog, PostgreSQL의 논리적 디코딩 등을 이용하며, 이를 Kafka로 보내는 Debezium 같은 도구가 널리 쓰입니다.

CDC는 보통 비동기입니다. 즉 파생 시스템은 항상 조금 뒤처지며, 복제 지연의 모든 문제를 그대로 물려받습니다.

12.2 처음부터 다 갖고 있지 않을 때

스냅숏에서 시작하거나, 로그를 압축한다

초기 스냅숏 snapshot

검색 인덱스를 새로 만들려면 전체 데이터가 필요하지만, 변경 로그를 태초부터 전부 보관하는 것은 비현실적입니다.

그래서 DB의 일관된 스냅숏을 먼저 적재하고, 그 스냅숏이 대응하는 로그 위치부터 변경을 이어 적용합니다.

로그 컴팩션 log compaction

같은 키에 대한 갱신이 여러 번 있었다면, 가장 최신 값만 남기고 나머지를 버립니다. 삭제는 널 값(tombstone)으로 표시합니다.

그러면 로그의 크기는 데이터베이스의 현재 크기에 비례하게 되고, 별도의 스냅숏 없이 로그만으로 전체 상태를 복원할 수 있습니다.

로그 구조 저장 엔진의 컴팩션과 같은 아이디어이며, Kafka도 이 기능을 제공합니다.

이 지점에서 로그는 더 이상 "지나가는 메시지 큐"가 아닙니다. 데이터베이스의 완전한 사본을 담을 수 있는 저장소가 됩니다.
12.2 이벤트 소싱 event sourcing

변경을 "추출"하지 말고, 처음부터 이벤트로 쓴다

이벤트 소싱은 애플리케이션의 상태 변화를 불변 이벤트의 추가 전용 로그로 저장합니다. 데이터베이스를 갱신하는 것이 아니라, 일어난 일을 기록합니다.

CDC와 결정적으로 다른 점은 추상화 수준입니다.

  • CDC — DB 수준의 저수준 변경. "테이블 X의 행 Y가 이렇게 바뀜". 원본 DB가 진실이고 로그는 부산물입니다.
  • 이벤트 소싱 — 도메인 수준의 사건. "학생이 이 강의 등록을 취소함". 로그 자체가 진실이고 DB는 파생물입니다.

그래서 이벤트 소싱의 로그는 지울 수도, 덮어쓸 수도 없습니다. 잘못을 되돌리려면 취소 이벤트를 추가합니다.

컴팩션을 쓸 수 없다

CDC 로그는 같은 키의 최신 값만 남겨도 상태가 보존됩니다. 갱신이 이전 값을 완전히 대체하기 때문입니다.

그러나 이벤트 소싱의 이벤트는 의미가 누적됩니다. "장바구니에 3개 추가"는 이전 이벤트를 대체하지 않습니다. 하나라도 버리면 현재 상태를 계산할 수 없습니다.

그래서 이벤트 소싱은 스냅숏으로 성능을 얻습니다. 스냅숏은 어디까지나 최적화이며, 진실은 여전히 전체 로그입니다.

12.2 명령과 이벤트

검증은 명령에서, 기록은 이벤트로

명령 command

사용자의 요청입니다. 아직 실패할 수 있습니다 — 재고가 없거나, 좌석이 이미 팔렸거나, 유효성 검사에 걸릴 수 있습니다.

이벤트 event

명령이 검증을 통과한 뒤 만들어지는 기정사실입니다. 이미 일어난 일이므로 거부될 수 없습니다.

그래서 순서가 중요하다

검증은 이벤트를 기록하기 전에, 동기적으로 끝나야 합니다. 일단 로그에 들어간 이벤트는 소비자들이 무조건 적용하기 때문입니다.

예약 시스템이라면 — 좌석 중복을 막는 검증은 명령 처리 단계에서 하고, 통과한 것만 "좌석 예약됨" 이벤트로 남깁니다. 필요하다면 "예약 시도됨"과 "예약 확정됨"을 나눠 검증을 비동기로 미룰 수도 있습니다.
12.2 현재 상태 도출

상태는 "이벤트 로그를 접은 결과"다

이벤트 로그만으로는 사용자에게 보여줄 것이 없습니다. 필요한 것은 현재 상태입니다. 그래서 로그를 순서대로 적용해 상태를 만듭니다.

여기서 중요한 성질은 결정론입니다. 같은 로그를 같은 순서로 적용하면 항상 같은 상태가 나옵니다. 그래서 파생 상태는 언제든 버리고 다시 만들 수 있습니다.

이 구조는 읽기와 쓰기의 형태를 분리합니다. 쓰기는 이벤트 추가, 읽기는 목적에 맞게 최적화된 뷰 — 이것이 CQRS입니다. 같은 로그에서 서로 다른 여러 뷰를 만들 수 있습니다.

비유

상태는 변경 스트림의 시간 적분이고, 변경 스트림은 상태의 시간 미분입니다.

데이터베이스와 로그는 서로 다른 두 개의 것이 아니라, 같은 정보의 두 표현입니다. 로그가 있으면 언제든 DB를 만들 수 있고, DB만 있으면 과거는 사라집니다.

12.2 불변성의 힘

과거를 지우지 않으면 할 수 있는 일들

  • 감사와 진단 — 어떻게 이 상태에 도달했는지 그대로 추적할 수 있습니다. 회계 장부가 정정 분개를 추가하는 방식과 같습니다.
  • 버그로부터의 복구 — 잘못된 코드가 상태를 망쳤다면, 로그는 멀쩡하므로 코드를 고쳐 다시 계산하면 됩니다. 파괴적 갱신은 이 복구를 불가능하게 만듭니다.
  • 여러 뷰의 동시 존재 — 같은 로그로 새 뷰를 만들어 기존 뷰와 나란히 운영하다가 전환할 수 있습니다. 위험한 스키마 마이그레이션이 필요 없어집니다.
  • 과거의 재해석 — 나중에 필요해진 질문을 이미 지나간 데이터에 던질 수 있습니다.
사고방식의 전환

"장바구니에서 상품을 삭제했다"는 사실은, DB에서 행을 지우면 사라집니다.

그러나 이벤트로 남기면 "담았다가 뺐다"는 정보가 보존되고, 이것은 추천이나 이탈 분석에 값진 데이터가 됩니다.

즉 불변 로그는 지금 필요한 정보만이 아니라, 미래에 필요할지 모르는 정보까지 보존합니다.

12.2 불변성의 한계

"영원히 남는다"는 것이 항상 좋기만 할까

정말 지워야 할 때

개인정보 삭제 요구나 법적 의무처럼, 데이터를 실제로 없애야 하는 경우가 있습니다. 추가 전용 로그와 정면으로 충돌합니다.

파생 뷰에서 지우는 것만으로는 부족합니다. 로그와 백업, 그리고 모든 사본에서 지워야 합니다. 이것은 생각보다 훨씬 어렵습니다.

로그의 성장

변경이 잦은 데이터에서 로그는 매우 빠르게 커집니다. 컴팩션이 가능한 경우도 있지만, 이벤트 소싱에서는 쉽지 않습니다.

비동기가 만드는 틈

이벤트를 기록한 직후 자신의 뷰를 읽으면 아직 반영되지 않은 상태를 볼 수 있습니다. 이 틈을 메우려면 읽기 뷰를 동기적으로 갱신하거나, 자신의 쓰기를 읽기 보장을 별도로 설계해야 합니다.

여러 객체에 걸친 동시성 제어도 로그 하나만으로는 해결되지 않습니다.

그리고 현실적인 이유로 삭제는 종종 불완전합니다 — "데이터를 지운다"는 것은 흔히 "찾기 어렵게 만든다"에 가깝고, 어딘가의 사본에는 남아 있습니다.

스트림 처리

스트림을 받아서 무엇을 할 것인가. 그리고 끝나지 않는 데이터에서 "시간"과 "정확성"을 어떻게 정의할 것인가.

12.3 스트림으로 무엇을 하는가

스트림의 세 가지 용도

저장한다

이벤트를 DB·캐시·검색 인덱스로 흘려보내 다른 클라이언트가 질의할 수 있게 만듭니다. 12.2절에서 본 파생 뷰 유지가 여기에 해당합니다.

사람에게 알린다

이메일·푸시 알림을 보내거나 실시간 대시보드를 갱신합니다. 사람이 최종 소비자입니다.

새 스트림을 만든다

하나 이상의 입력 스트림을 처리해 또 다른 출력 스트림을 냅니다. 이렇게 연결된 처리 단계들이 연산자 파이프라인을 이룹니다.

배치 잡과 닮았지만 결정적 차이가 있습니다 — 스트림 잡은 끝나지 않습니다. 그래서 정렬은 쓸 수 없고, 내결함성 방식도 달라지며(재실행으로 때울 수 없음), 시간을 다루는 문제가 새로 등장합니다.
12.3 스트림 처리의 용례

질의가 머무르고, 데이터가 흘러간다

복합 이벤트 처리 CEP

이벤트 흐름 속의 특정 패턴을 찾습니다. SQL과 비슷한 선언적 언어로 패턴을 기술하면, 엔진이 상태 기계를 유지하며 일치하는 순간에 복합 이벤트를 냅니다.

관계가 뒤집힙니다 — DB에서는 데이터가 오래 머물고 질의가 지나가지만, CEP에서는 질의가 오래 머물고 데이터가 지나갑니다.

스트림 분석 analytics

개별 패턴보다 집계 지표에 관심이 있습니다. 일정 기간의 건수·평균·비율·추세를 계산합니다.

정확한 값보다 근사치로 충분한 경우가 많아, 확률적 알고리즘이 널리 쓰입니다.

  • 집합 원소 확인 — 블룸 필터
  • 고유 개수 추정 — HyperLogLog
  • 백분위 추정 — t-digest 계열

근사는 최적화 수단일 뿐입니다. 스트림 처리가 본질적으로 부정확한 것은 아닙니다.

12.3 그 밖의 용례

같은 도구, 다른 목적

구체화 뷰 유지

집계와 결정적으로 다른 점 — 구체화 뷰는 특정 기간의 윈도가 아니라 전체 역사가 필요합니다. 그래서 원칙적으로 영구적인 윈도를 유지하며, 컴팩션으로 크기를 관리합니다.

스트림에서의 검색

여러 개의 질의를 미리 등록해 두고, 새 문서가 흘러올 때마다 어떤 질의에 걸리는지 봅니다. 문서를 인덱싱하는 대신 질의를 인덱싱합니다.

메시지 전달과 RPC

액터 모델 같은 메시지 전달 프레임워크는 겉보기가 비슷하지만 다른 도구입니다. 액터는 동시성 관리가 목적이고, 스트림 처리는 데이터 파이프라인이 목적입니다.

액터의 통신은 일대일이며 순서 보장이나 재생을 제공하지 않는 경우가 많습니다.

12.3 시간에 대한 추론

이벤트 시각 vs 처리 시각

10:00~10:01 윈도의 집계 — 지연 도착 이벤트
허용 지연

윈도를 언제 닫을지 정해야 결과를 낼 수 있지만, "이제 다 왔다"는 것을 확신할 방법은 없습니다. 허용 지연을 늘리면 정확해지고, 줄이면 빨라집니다.

12.3 처리 시각의 함정

처리 시각으로 집계하면 "사건"이 아니라 "장비"를 측정한다

이벤트에는 두 개의 시각이 있습니다 — 실제로 일어난 이벤트 시각과, 처리기가 그것을 본 처리 시각입니다. 둘의 차이는 큐 대기, 네트워크 결함, 소비자 재시작 등으로 예측할 수 없이 벌어집니다.

처리 시각을 기준으로 집계하면 이런 왜곡이 생깁니다:

  • 처리기가 30초 멈췄다가 재개하면, 그 순간 가짜 급증이 나타납니다. 실제 이벤트 발생량은 평탄했는데도요.
  • 멈춰 있던 구간은 가짜 공백으로 보입니다.
  • 코드를 고쳐 과거를 재처리하면, 모든 이벤트가 지금 한꺼번에 일어난 것처럼 보입니다.

그래서 의미 있는 지표를 원하면 이벤트 시각을 기준으로 삼아야 합니다.

스트래글러 straggler

윈도를 닫은 뒤에 그 윈도에 속하는 이벤트가 도착하는 일은 늘 있습니다.

대응은 둘 중 하나입니다 — 무시하고 버리기(버린 비율을 지표로 감시), 또는 보정 값을 내보내 이전 결과를 갱신하기.

전자는 단순하고 후자는 정확합니다. 어느 쪽이든 "완료"는 추정일 뿐이라는 사실은 변하지 않습니다.

12.3 누구의 시계를 믿을 것인가

이벤트 시각은 흔히 "믿을 수 없는 기기"가 찍는다

모바일 앱이 오프라인 상태에서 이벤트를 모아 뒀다가 나중에 보내는 경우, 이벤트 시각은 사용자 기기의 시계가 찍습니다. 그 시계는 틀릴 수 있고, 심지어 의도적으로 조작될 수도 있습니다.

서버 도착 시각은 신뢰할 수 있지만, 그것은 사건이 일어난 시각이 아닙니다.

실용적인 해법은 세 개의 타임스탬프를 함께 기록하는 것입니다.

시계 오차 보정 기법
  • ① 기기 시계로 본 이벤트 발생 시각
  • ② 기기 시계로 본 서버 전송 시각
  • ③ 서버 시계로 본 도착 시각

③ − ②는 기기 시계와 서버 시계의 오차를 추정합니다(네트워크 지연이 무시할 만하다고 가정).

이 오차를 ①에 적용하면 서버 시계 기준의 실제 발생 시각을 얻습니다.

두 값이 같은 시계로 측정됐다는 점이 핵심입니다. 그래서 시계가 틀려도 차이는 의미가 있습니다.

12.3 윈도의 종류

무한 스트림을 유한한 조각으로 자르는 네 가지 방법

텀블링 tumbling

고정 길이, 겹치지 않음. 각 이벤트는 정확히 하나의 윈도에 속합니다.

예: 1분 단위 구간

호핑 hopping

고정 길이지만 겹칩니다. 5분 길이를 1분마다 시작하면, 이동 평균처럼 매끄러운 곡선을 얻습니다.

슬라이딩 sliding

고정된 경계 없이, 서로 일정 시간 안에 있는 이벤트끼리 묶습니다. 버퍼에서 오래된 이벤트를 밀어내며 유지합니다.

세션 session

길이가 정해져 있지 않습니다. 같은 사용자의 이벤트를 묶고, 활동이 끊긴 시간이 일정 기준을 넘으면 종료합니다.

사용자 행동 분석의 기본 단위

어떤 윈도를 쓰든, "이 윈도가 완료되었다"고 판단하는 기준(워터마크)은 여전히 별도로 결정해야 합니다.
12.3 스트림 조인

조인은 세 가지 종류로 나뉜다

1

스트림-스트림

두 개의 이벤트 스트림을, 일정 시간 윈도 안에서 짝지어 조인합니다.

2

스트림-테이블

이벤트에 데이터베이스의 정보를 덧붙입니다(enrichment).

3

테이블-테이블

두 테이블의 변경 스트림을 조인해 구체화 뷰를 유지합니다.

세 조인 모두에서 상태(state)가 등장합니다. 스트림 처리기는 조인을 하기 위해 과거의 일부를 기억해야 하고, 이 상태를 안전하게 유지하는 것이 곧 내결함성 문제가 됩니다.
12.3 스트림-스트림 조인

윈도 조인 — "검색 후 클릭했는가"

검색 이벤트와 클릭 이벤트가 각각 별개의 스트림으로 들어옵니다. 검색 결과의 품질을 알려면 어떤 검색이 클릭으로 이어졌는지 짝을 지어야 합니다.

단순히 세션 ID로 조인하면 될 것 같지만, 문제는 시간입니다. 클릭은 검색 직후일 수도, 몇 분 뒤일 수도, 아예 없을 수도 있습니다.

그래서 처리기는 상태를 유지합니다 — 세션 ID로 색인된 최근 이벤트들을 보관하고, 반대쪽 이벤트가 오면 짝을 맞춰 내보냅니다.

"클릭 없음"도 결과다

클릭률을 계산하려면 클릭되지 않은 검색도 알아야 합니다. 그런데 "클릭이 없었다"는 사실은 기다려 봐야만 알 수 있습니다.

그래서 윈도 만료 시점에 타이머를 걸어, 짝을 찾지 못한 검색 이벤트를 "클릭 없음"으로 확정해 내보냅니다.

이벤트가 순서대로 오지 않을 수 있으므로, 윈도는 지연 도착을 감당할 만큼 넉넉해야 합니다.

12.3 스트림-테이블 조인

이벤트를 DB 정보로 살 붙이기

활동 이벤트에는 보통 사용자 ID만 들어 있습니다. 분석에 쓰려면 나이·지역 같은 프로필 정보를 붙여야 합니다.

가장 단순한 방법은 이벤트마다 원격 DB에 질의하는 것입니다. 하지만 이는 느리고, DB에 과부하를 주며, 결과가 결정론적이지 않습니다.

더 나은 방법은 DB의 사본을 스트림 처리기 안에 두고 로컬에서 조회하는 것입니다. 배치 처리에서 해시 조인을 위해 작은 테이블을 메모리에 올리던 것과 같은 발상입니다.

차이는 하나 — 배치의 스냅숏은 고정이지만, 스트림 잡은 영원히 실행되므로 사본이 계속 갱신되어야 합니다.

여기서 CDC가 다시 등장한다

DB의 변경 로그를 구독하면, 로컬 사본을 자동으로 최신 상태로 유지할 수 있습니다.

즉 이 조인은 두 스트림의 조인입니다 — 활동 이벤트 스트림과 프로필 변경 스트림.

다만 윈도가 다릅니다. 활동 이벤트는 특정 시점의 사건이고, 프로필 테이블은 지금까지의 모든 변경을 반영해야 합니다. 사실상 윈도의 길이가 무한한 조인입니다.

12.3 테이블-테이블 조인

구체화 뷰를 증분으로 유지한다

소셜 네트워크의 홈 타임라인을 생각해 봅시다. 사용자가 볼 때마다 "내가 팔로우한 사람들의 최근 글"을 조인하는 것은 너무 비쌉니다.

그래서 각 사용자의 타임라인을 미리 계산해 캐시합니다. 이 캐시가 곧 조인 결과의 구체화 뷰이며, 스트림 처리기가 이를 증분으로 갱신합니다.

처리기는 두 종류의 변경 스트림을 구독합니다 — 글 작성/삭제와 팔로우/언팔로우. 각 이벤트마다 영향받는 타임라인을 갱신합니다.

대응해야 할 변경들
  • 글 작성 → 작성자를 팔로우하는 모든 사용자의 타임라인에 추가
  • 글 삭제 → 모든 타임라인에서 제거
  • 팔로우 시작 → 상대의 최근 글을 내 타임라인에 추가
  • 팔로우 해제 → 상대의 글을 내 타임라인에서 제거

이런 뷰를 유지하려면 양쪽 테이블의 전체 역사가 필요합니다. 그래서 윈도는 사실상 무한이며, 상태는 컴팩션으로 관리합니다.

12.3 조인의 시간 의존성

같은 데이터라도, 언제 조인하느냐에 따라 답이 달라진다

세 조인 모두 상태를 유지하고, 상태를 바꾸는 이벤트를 순서대로 반영한다는 공통 구조를 갖습니다. 그렇다면 이벤트의 순서가 중요합니다.

세율이 바뀌는 순간을 생각해 봅시다. 판매 이벤트에 세율 테이블을 조인하는데, 파티션마다 이벤트가 도착하는 순서가 다르면 어떤 판매는 옛 세율, 어떤 판매는 새 세율로 계산됩니다.

결정론을 원한다면 답은 하나입니다 — 조인 시점의 최신 값이 아니라, 이벤트 시각에 유효했던 값을 써야 합니다. 그러려면 테이블의 버전 이력을 보관해야 합니다.

이름이 붙은 문제

데이터 웨어하우스에서는 이를 천천히 변하는 차원(slowly changing dimension, SCD)이라 부릅니다.

해법은 테이블의 각 버전에 고유한 식별자를 부여하고, 이벤트가 자신이 사용한 버전을 참조하도록 하는 것입니다.

이렇게 하면 조인이 결정론적이 되지만, 로그 컴팩션은 불가능해집니다. 모든 버전을 보관해야 하기 때문입니다. 여기서도 정확성과 비용이 교환됩니다.

12.3 내결함성

스트림 잡은 "끝나면 다시 실행"할 수 없다

배치 처리의 내결함성은 단순했습니다. 태스크가 실패하면 그 태스크만 다시 실행하고, 출력은 성공했을 때만 보이게 만들면 됩니다. 마치 실패가 없었던 것처럼 보이게 할 수 있었습니다 — 정확히 한 번의 의미론입니다.

스트림에서는 이 방식이 통하지 않습니다. 출력은 계속 흘러나가고, 입력은 끝이 없어서 "전부 다시 실행"이라는 개념 자체가 성립하지 않습니다.

그래서 두 가지 접근이 쓰입니다.

마이크로배칭

스트림을 아주 작은 배치로 쪼갭니다(예: 1초). 각 조각은 작은 배치 잡이므로 배치의 내결함성을 그대로 씁니다.

단순하지만, 배치 크기가 곧 텀블링 윈도가 되어 시간 처리에 제약이 생길 수 있습니다.

체크포인팅

일정 간격으로 상태의 스냅숏을 안정적인 저장소에 기록합니다. 장애가 나면 마지막 체크포인트로 되돌아가 그 지점부터 재시작합니다.

배치 크기와 무관하게 동작하므로 윈도 설계가 자유롭습니다.

12.3 원자적 커밋과 멱등성

"정확히 한 번"은 사실 "결과적으로 한 번"이다

체크포인트만으로는 부족합니다. 체크포인트 이후에 이미 외부로 내보낸 출력이 있다면, 재시작 시 같은 출력이 두 번 나갑니다. 외부 시스템은 되돌릴 수 없습니다.

그래서 필요한 것은 모든 부수 효과가 원자적으로 함께 반영되거나 함께 무효화되는 것입니다 — 출력 메시지, 상태 변경, 그리고 입력 오프셋 기록까지 하나의 단위로.

프레임워크 내부에서 같은 시스템 안의 상태와 출력만 다룬다면, 이 원자적 커밋을 훨씬 효율적으로 구현할 수 있습니다. 이것이 여러 스트림 처리 프레임워크가 제공하는 정확히 한 번(exactly-once) 보장의 실체입니다.

더 싼 방법 — 멱등성

여러 번 실행해도 한 번 실행한 것과 결과가 같은 연산으로 만들면, 중복 처리를 걱정하지 않아도 됩니다.

예: 키-값 저장소에 고정된 값을 쓰는 연산은 몇 번 해도 같습니다. 반면 카운터를 증가시키는 연산은 그렇지 않습니다.

멱등적이지 않은 연산도, 메시지 오프셋을 함께 기록해 두면 멱등적으로 만들 수 있습니다. 이미 처리한 오프셋의 갱신은 건너뜁니다.

주의: 처리 순서가 바뀌거나 여러 버전의 코드가 동시에 실행되면 이 가정이 깨질 수 있습니다.

"정확히 한 번"이라는 말은 오해를 부릅니다. 실제로는 중복을 어딘가에서 흡수해 겉으로는 한 번처럼 보이게 만드는 것이며, effectively-once가 더 정확한 표현입니다.
12.3 실패 후 상태 재구축

윈도와 조인 테이블은 어떻게 살려내는가

  • 원격 저장소에 상태를 두고 복제한다 — 안전하지만 이벤트마다 네트워크 왕복이 생겨 느립니다.
  • 로컬에 상태를 두고 주기적으로 복제한다 — 로컬 디스크에 상태를 유지하면서, 변경 로그를 원격에 남깁니다. 실패 시 이 로그로 상태를 재구성합니다.
  • 입력 스트림에서 다시 계산한다 — 상태 자체를 복제하지 않고, 로그를 되감아 상태를 재생합니다. 로그가 컴팩션되어 있다면 빠르게 복원할 수 있습니다.

어느 쪽이 유리한지는 상태의 크기와 재계산 비용에 달려 있습니다. 상태가 작으면 재계산이 싸고, 크면 복제가 낫습니다.

재계산이 늘 되는 것은 아니다

10분 윈도 집계처럼 짧은 역사만 필요한 상태는 다시 계산하면 됩니다.

그러나 몇 년간의 이벤트를 접어 만든 상태라면, 재계산은 몇 시간이 걸릴 수도 있습니다. 그런 상태는 반드시 복제해야 합니다.

또한 디스크에 있다는 것이 곧 안전을 뜻하지 않습니다. 로컬 디스크는 그 장비와 함께 사라질 수 있습니다.

요약 12장 정리 (1)

전달과 출처

두 종류의 메시지 브로커

  • AMQP/JMS 계열 — 개별 메시지를 소비자에 배정, ack 후 삭제. 처리 비용이 크고 순서가 무관한 작업 큐에 적합.
  • 로그 기반 — 파티션 내 모든 메시지를 순서대로 보관, 오프셋으로 위치 추적. 순서 보장 + 재생 가능, 처리량이 높음.

스트림은 어디서 오는가

  • 사용자 활동 이벤트, 센서 측정값, 시장 데이터 등 본래 이벤트인 것들
  • 변경 데이터 캡처(CDC) — 기존 DB의 쓰기를 스트림으로 변환
  • 이벤트 소싱 — 애초에 불변 이벤트로 쓰기

어느 쪽이든 핵심은 같습니다 — 순서가 보장된 불변 로그 하나를 진실의 원천으로 두고, 나머지를 파생 뷰로 유지합니다. 그러면 이중 쓰기의 불일치가 구조적으로 사라집니다.

요약 12장 정리 (2)

시간 · 조인 · 내결함성

시간

지표는 이벤트 시각 기준이어야 의미가 있습니다. 처리 시각 기준은 처리기의 사정을 측정할 뿐입니다.

스트래글러는 항상 있고, "윈도가 완료됐다"는 판단은 결국 추정입니다. 버리거나 보정하거나, 둘 중 하나를 선택해야 합니다.

세 가지 조인

스트림-스트림은 윈도 안에서 짝을 맞추고, 스트림-테이블은 CDC로 유지한 로컬 사본으로 이벤트를 살찌우며, 테이블-테이블은 구체화 뷰를 증분 갱신합니다.

모두 순서 의존적이므로, 결정론을 원하면 버전 이력이 필요합니다.

내결함성

마이크로배칭과 체크포인팅으로 재시작 지점을 만들고, 원자적 커밋 또는 멱등성으로 중복의 효과를 지웁니다.

결과는 "정확히 한 번"처럼 보이지만, 실제로는 중복을 흡수한 것입니다.

12장의 결론

상태는 스냅숏,
로그는 진실

데이터베이스는 이벤트 로그를 접어 만든 캐시일 뿐입니다. 이 관점을 받아들이면 파생 데이터를 유지하는 일이 동기화 문제에서 스트림 문제로 바뀌고, 파생 뷰는 언제든 버리고 다시 만들 수 있는 것이 됩니다.

불변 로그가 원천파생 뷰는 재생 가능이벤트 시각이 진짜 시간중복은 흡수한다
