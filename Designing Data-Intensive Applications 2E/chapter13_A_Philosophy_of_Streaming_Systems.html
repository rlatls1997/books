13.1 데이터플로에 대해 추론하기

어디에 먼저 쓰는가 — 이것이 전부를 결정한다

같은 데이터의 사본을 여러 저장소에 유지해야 한다면 입력과 출력을 아주 명확히 해야 합니다. 데이터는 어디에 먼저 쓰이고, 어떤 표현이 어떤 원본에서 파생되는가?

실험 · 두 클라이언트가 동시에 쓰기를 보낸다
버튼을 눌러 두 방식을 비교해 보세요.

모든 사용자 입력을 쓰기 순서를 결정하는 단일 시스템으로 흘려보낼 수 있다면, 같은 순서로 처리하여 다른 표현을 파생하는 일이 훨씬 쉬워진다 — 상태 기계 복제(state machine replication)의 응용이다. CDC냐 이벤트 소싱 로그냐보다 전체 순서를 정한다는 원칙이 중요하다.

13.1 파생 데이터 vs 분산 트랜잭션

같은 목표, 다른 수단

분산 트랜잭션

원자적 커밋 프로토콜로 변경이 원자적으로 적용되도록 보장합니다.

쓰고 나면 즉시 최신 값을 읽을 수 있습니다(자신의 쓰기 읽기).

그러나 XA는 결함 감내와 성능 특성이 나빠 유용성이 크게 제한됩니다. 더 나은 프로토콜이 가능할지 몰라도, 널리 채택되어 기존 도구와 통합되기까지는 가까운 미래에 일어날 것 같지 않습니다.

로그 기반 파생 데이터

결정론적 재시도 + 멱등성으로 정확성을 달성합니다.

대신 비동기 업데이트라서 읽기가 최신임을 기본 보장하지 않습니다.

좋은 분산 트랜잭션 프로토콜이 널리 지원되지 않는 현실에서, 서로 다른 데이터 시스템을 통합하는 가장 유망한 접근입니다.

다만 "결과적 일관성은 피할 수 없으니 그냥 받아들이라"고 말하는 것은 (대처법에 대한 좋은 안내 없이는) 생산적이지 않습니다. 이 장 후반에서 비동기 파생 시스템 위에 더 강한 보장을 구현하는 접근을 다뤄, 두 세계의 중간 지대를 찾아갑니다.
13.1 전체 순서의 한계

규모가 커지면 "하나의 순서"가 무너진다

시스템이 충분히 작으면 전체 순서 이벤트 로그를 만드는 일은 완전히 실현 가능합니다(단일 리더 복제의 인기가 그 증거). 그러나 커질수록 한계가 드러납니다.

처리량이 한 대를 넘어설 때

전체 순서 로그는 보통 모든 이벤트가 단일 리더 노드를 통과해야 합니다. 처리량이 넘치면 로그를 샤딩해야 하고, 그러면 두 샤드 간 순서는 모호해집니다.

지리적으로 분산될 때

데이터센터 전체 장애를 견디려면 각 DC에 별도 리더를 두게 됩니다(동기 크로스 DC 조정은 비효율적). 서로 다른 DC에서 생긴 이벤트의 순서는 정의되지 않습니다.

마이크로서비스일 때

각 서비스와 그 내구성 상태를 독립 단위로 배포하고 상태를 공유하지 않는 것이 일반적인 설계입니다. 서로 다른 서비스에서 생긴 두 이벤트에는 정의된 순서가 없습니다.

클라이언트 상태가 있을 때

사용자 입력에 즉시 반응하고 오프라인에서도 동작하는 앱에서는 클라이언트와 서버가 서로 다른 순서로 이벤트를 보게 될 가능성이 매우 큽니다.

형식적으로 이벤트의 전체 순서를 정하는 것은 전체 순서 브로드캐스트이며, 이는 합의와 동등합니다. 대부분의 합의 알고리즘은 단일 노드 처리량이 전체 스트림을 감당한다고 가정하며, 여러 노드가 순서 결정을 분담하는 메커니즘은 제공하지 않습니다.

친구를 끊고 나서 보낸 메시지가, 먼저 도착한다면

실험 · 언프렌드 → 메시지 전송의 인과 의존성
‘다음 단계’를 눌러 진행하세요.

인과 링크가 없다면 동시 이벤트를 임의 순서로 배열해도 문제없습니다. 같은 객체의 여러 업데이트는 객체 ID로 같은 로그 샤드에 라우팅하면 전체 순서가 잡힙니다. 그러나 인과 의존성은 이처럼 더 미묘하게 나타납니다 — 여기서 알림은 사실상 메시지와 친구 목록의 조인입니다.

간단한 답은 없다 — 그래도 시작점은 있다

논리적 타임스탬프

코디네이션 없이 전체 순서를 제공하므로, 전체 순서 브로드캐스트가 불가능할 때 도움이 됩니다.

단, 수신자가 순서 어긋난 이벤트를 처리해야 하고 추가 메타데이터를 전달해야 합니다.

본 것을 기록하기

사용자가 결정을 내리기 전에 본 시스템 상태를 이벤트로 기록하고 고유 식별자를 부여하면, 이후 이벤트들이 그 ID를 참조해 인과 의존성을 남길 수 있습니다.

충돌 해소 알고리즘

예상치 못한 순서로 도착한 이벤트 처리에 도움이 됩니다. 상태 유지에는 유용하지만, 알림 발송처럼 외부 부작용이 있는 행위에는 도움이 되지 않습니다.

미래에는 모든 이벤트를 전체 순서 브로드캐스트라는 병목으로 몰아넣지 않고도, 인과 의존성을 효율적으로 포착하고 파생 상태를 올바르게 유지하는 애플리케이션 개발 패턴이 등장할지도 모릅니다.
13.1 배치와 스트림 처리

파생 상태를 유지하는 도구

데이터 통합의 목표는 데이터가 올바른 형태로 올바른 모든 곳에 도달하게 하는 것입니다. 입력 소비, 변환, 조인, 필터, 집계, 모델 학습, 평가, 그리고 적절한 출력에 쓰기 — 배치와 스트림 프로세서가 그 도구입니다.

둘은 많은 원리를 공유하며, 근본적 차이는 하나입니다: 스트림 프로세서는 무한(unbounded) 데이터셋을, 배치는 알려진 유한 크기의 입력을 다룹니다.

배치 처리는 (함수형 언어로 쓰지 않아도) 강한 함수형 색채를 띱니다 — 결정론적 순수 함수, 불변 입력, 추가 전용 출력. 스트림 처리도 비슷하되, 관리되는 결함 감내 상태를 연산자에 허용합니다.

잘 정의된 입출력을 가진 결정론적 함수라는 원칙은 결함 감내에만 좋은 게 아니라, 조직 전체의 데이터플로를 추론하기 쉽게 만듭니다. 파생 데이터가 검색 인덱스든 통계 모델이든 캐시든, "하나에서 다른 하나를 파생하는 파이프라인"으로 생각하면 됩니다.
원리상 파생 시스템을 동기적으로 유지할 수도 있습니다(관계형 DB가 같은 트랜잭션에서 보조 인덱스를 갱신하듯). 그러나 비동기성이야말로 이벤트 로그 기반 시스템을 견고하게 만듭니다 — 결함이 국소적으로 격리되기 때문입니다.
반대로 분산 트랜잭션은 참가자 하나만 실패해도 중단되므로, 실패를 시스템 전체로 증폭시키는 경향이 있습니다.
13.1 재처리와 애플리케이션 진화

철도 궤간을 바꾸는 방법 — 세 번째 레일

파생 데이터 유지에는 둘 다 유용합니다. 스트림 처리는 입력 변화를 낮은 지연으로 반영하고, 배치 처리는 누적된 대량의 과거 데이터를 재처리해 새로운 뷰를 만들 수 있게 합니다.

재처리가 없다면 스키마 진화는 "선택적 필드 추가" 정도로 제한됩니다. 재처리가 있으면 데이터셋을 완전히 다른 모델로 재구성할 수 있습니다.

파생 뷰는 점진적 진화를 가능하게 합니다. 구 스키마와 신 스키마를 같은 원본에서 파생된 두 개의 독립적인 뷰로 나란히 유지하고, 소수 사용자를 새 뷰로 옮겨 성능과 버그를 확인한 뒤 비율을 늘리고, 마지막에 구 뷰를 버립니다.

철도의 스키마 마이그레이션

19세기 영국에는 여러 궤간(gauge) 표준이 경쟁했고, 서로 다른 궤간의 선로에서는 열차가 달릴 수 없어 연결이 제한됐습니다.

1846년 표준 궤간이 정해진 뒤, 노선을 몇 달·몇 년 닫지 않고 어떻게 바꿀까요? 답은 세 번째 레일을 추가해 이중 궤간(dual gauge)으로 만드는 것. 점진적으로 전환할 수 있고, 그동안 두 궤간의 열차가 모두 달릴 수 있으며, 모두 표준으로 바뀐 뒤 비표준 레일을 제거합니다.

다만 비용이 커서 비표준 궤간은 오늘날에도 남아 있습니다 — 예를 들어 샌프란시스코 베이 지역의 BART는 미국 대부분과 다른 궤간을 씁니다.

점진적 마이그레이션의 아름다움은 모든 단계가 되돌릴 수 있다는 점입니다. 언제나 돌아갈 수 있는 동작하는 시스템이 있습니다. 되돌릴 수 없는 손상의 위험을 줄이면 더 자신 있게, 더 빠르게 시스템을 개선할 수 있습니다.
13.1 배치와 스트림의 통합

람다에서 카파로

배치와 스트림을 통합하려는 초기 제안은 람다 아키텍처였지만, 여러 문제가 있어 이제는 쓰이지 않습니다.

최근 시스템들은 과거 데이터 재처리(배치)와 도착하는 이벤트 처리(스트림)를 같은 시스템에서 구현할 수 있게 하는데, 이를 카파 아키텍처라 부르기도 합니다.

  • 재생(replay) — 최근 이벤트를 처리하는 같은 엔진으로 과거 이벤트를 다시 흘릴 수 있어야 합니다. 로그 기반 브로커는 메시지 재생이 가능하고, 일부 스트림 프로세서는 분산 파일시스템·객체 스토리지에서 입력을 읽습니다.
  • 정확히 한 번 의미 — 결함이 실제로 발생했어도 출력이 결함이 없었던 것과 같도록 보장해야 합니다. 배치처럼 실패한 태스크의 부분 출력을 버려야 합니다.
  • 이벤트 시간 윈도잉 — 처리 시간이 아니라 이벤트 시간으로 윈도우를 나눠야 합니다. 과거를 재처리할 때 처리 시간은 무의미하기 때문입니다. Apache Beam이 그런 계산을 표현하는 API를 제공하고, Flink나 Google Cloud Dataflow에서 실행됩니다.

13.2 저장 기술의 조합

CREATE INDEX를 실행하면 무슨 일이 벌어지는가

  • 테이블의 일관된 스냅숏을 스캔한다
  • 인덱싱 대상 필드 값을 골라내고 정렬한다
  • 인덱스를 기록한다
  • 스냅숏 이후 쌓인 쓰기 백로그를 처리한다 (테이블을 잠그지 않았다면)
  • 이후 트랜잭션이 테이블에 쓸 때마다 인덱스를 계속 최신으로 유지한다
이 과정은 새 팔로워 복제본을 세우는 것과, 그리고 스트리밍 시스템에서 CDC를 부트스트랩하는 것과 놀랄 만큼 닮았습니다.

즉 CREATE INDEX를 실행할 때마다 데이터베이스는 기존 데이터셋을 재처리해서 인덱스를 기존 데이터에 대한 새로운 뷰로 파생합니다. 기존 데이터가 변경 로그가 아니라 상태의 스냅숏일 수는 있지만, 둘은 밀접히 관련됩니다.

지금까지 우리가 본 데이터베이스 기능들 — 보조 인덱스(필드 값으로 효율적 검색), 구체화 뷰(질의 결과의 사전 계산 캐시), 복제 로그(다른 노드의 사본 최신 유지), 전문 검색 인덱스 — 은 11·12장에서 배치·스트림 프로세서로 만든 것들과 평행합니다.

13.2 만물의 메타 데이터베이스

조직 전체의 데이터플로가 하나의 거대한 데이터베이스처럼 보인다

배치, 스트림, ETL 프로세스가 데이터를 한 장소·형태에서 다른 장소·형태로 옮길 때마다, 그것은 인덱스나 구체화 뷰를 최신으로 유지하는 데이터베이스 서브시스템처럼 행동합니다.

이렇게 보면 배치·스트림 프로세서는 트리거, 저장 프로시저, 구체화 뷰 유지 알고리즘의 정교한 구현이고, 그들이 유지하는 파생 데이터 시스템은 서로 다른 인덱스 유형입니다.

차이는, 이런 기능들이 단일 통합 제품의 기능이 아니라 서로 다른 머신에서 다른 팀이 운영하는 여러 소프트웨어로 제공된다는 점입니다.

전제

단 하나의 데이터 모델이나 저장 형식이 모든 접근 패턴에 적합하지 않다면, 서로 다른 도구를 하나의 응집된 시스템으로 조합하는 길은 두 갈래입니다.

② 쓰기를 통합하는 언번들링

13.2 페더레이션 vs 언번들링

같은 동전의 양면

비교 · 읽기를 통합할까, 쓰기를 통합할까
두 접근을 번갈아 보세요.
페더레이션(폴리스토어) — 다양한 저장 엔진과 처리 방식에 통합 질의 인터페이스를 제공합니다. PostgreSQL의 foreign data wrapper, 그리고 Trino·Hoptimator·Xorq 같은 페더레이션 질의 엔진이 이 패턴입니다. 고수준 질의 언어와 우아한 의미론을 갖춘 관계형 전통이지만, 구현은 복잡합니다.
언번들링 — 페더레이션은 읽기를 다루지만 쓰기 동기화에 좋은 답이 없습니다. 여러 저장 시스템을 조합할 때 모든 변경이 결함 속에서도 올바른 곳에 도달하게 해야 합니다. CDC와 이벤트 로그로 저장 시스템을 안정적으로 끼워 맞추기 쉽게 만드는 것은, DB의 인덱스 유지 기능을 언번들링하는 일입니다. 한 가지를 잘하는 작은 도구들이 균일한 저수준 API(파이프)로 통신하고 고수준 언어(셸)로 조합되는 Unix 전통입니다.
13.2 언번들링을 작동시키기

기술 경계를 넘는 쓰기는 비동기 로그 + 멱등성

페더레이션의 읽기 전용 질의는 데이터 모델을 서로 매핑하는 문제로, 생각은 필요하지만 다룰 만한 문제입니다. 여러 저장 시스템의 쓰기를 동기화하는 것이 더 어려운 엔지니어링 문제입니다.

전통적 방식은 이종 저장 시스템 간 분산 트랜잭션인데, 앞서 보았듯 문제가 많습니다. 단일 저장·스트림 처리 시스템 내부의 트랜잭션은 실현 가능하지만, 데이터가 다른 기술의 경계를 넘을 때는 멱등 쓰기를 갖춘 비동기 이벤트 로그가 훨씬 견고하고 실용적입니다.

예컨대 일부 스트림 프로세서는 내부적으로 분산 트랜잭션으로 정확히 한 번 의미를 달성하고, 이는 꽤 잘 동작합니다. 그러나 다른 사람들이 만든 시스템(스트림 프로세서 → 분산 KV 저장소나 검색 인덱스)이 얽히면 표준 트랜잭션 프로토콜의 부재가 통합을 훨씬 어렵게 만듭니다.

로그 기반 통합의 큰 장점 — 느슨한 결합

시스템 수준 — 비동기 이벤트 스트림은 개별 컴포넌트의 장애나 성능 저하에 시스템 전체를 견고하게 만듭니다. 소비자가 느려지거나 실패하면 로그가 메시지를 버퍼링하므로 생산자와 다른 소비자는 영향 없이 계속 돌아갑니다. 고친 뒤 따라잡을 수 있어 데이터를 놓치지 않고 결함이 격리됩니다.
반면 분산 트랜잭션의 동기적 상호작용은 국소 결함을 대규모 장애로 확대시키는 경향이 있습니다.
인간 수준 — 언번들링은 컴포넌트와 서비스를 다른 팀이 독립적으로 개발·개선·유지할 수 있게 합니다. 이벤트 로그는 (내구성과 순서 덕에) 꽤 강한 일관성 속성을 담을 만큼 강력하면서도, 거의 모든 종류의 데이터에 적용될 만큼 범용적인 인터페이스입니다.
13.2 언번들링 vs 통합 시스템

깊이가 아니라 넓이 — 언제 하지 말아야 하는가

언번들링이 미래가 된다 해도 데이터베이스를 대체하지는 않습니다. 스트림 프로세서의 상태 유지와 배치·스트림 출력의 질의 제공을 위해 여전히 필요하고, 특정 워크로드용 전문 질의 엔진(예: 데이터 웨어하우스)도 계속 중요합니다.

여러 인프라를 운영하는 복잡성은 문제입니다. 각 소프트웨어에는 학습 곡선, 설정 문제, 운영 특이점이 있으니 움직이는 부품은 가능한 적게 배치하는 게 좋습니다. 단일 통합 제품이 설계된 워크로드에서는 더 좋고 예측 가능한 성능을 낼 수도 있습니다.

필요하지 않은 규모를 위해 만드는 것은 낭비이며 유연하지 못한 설계에 갇히게 합니다 — 사실상 조급한 최적화입니다.

언번들링의 목표

개별 데이터베이스와 특정 워크로드의 성능으로 경쟁하는 것이 아닙니다. 여러 데이터베이스를 결합해, 단일 소프트웨어로는 불가능한 훨씬 넓은 범위의 워크로드에서 좋은 성능을 얻는 것입니다.

깊이가 아니라 넓이(breadth, not depth)에 관한 이야기입니다.

따라서 하나의 기술이 필요한 모든 것을 해준다면 그것을 쓰는 편이 최선입니다. 저수준 컴포넌트로 직접 재구현하려 하지 마세요. 언번들링과 조합의 이점은 어떤 단일 소프트웨어도 요구사항을 만족시키지 못할 때에만 등장합니다.
조합 도구는 좋아지고 있습니다 — Debezium은 많은 DB에서 변경 스트림을 추출하고, Kafka 프로토콜은 이벤트 스트림의 사실상 표준이 되어가며, 증분 뷰 유지 엔진은 복잡한 질의의 캐시를 미리 계산하고 갱신할 수 있게 합니다.
13.2 데이터플로 중심 설계

1979년 VisiCalc이 이미 갖고 있던 것

기반 데이터가 바뀌면 파생 데이터를 갱신한다는 생각은 전혀 새롭지 않습니다. 스프레드시트는 강력한 데이터플로 프로그래밍 능력을 갖고 있습니다 — 한 셀에 수식을 넣으면, 입력이 바뀔 때마다 결과가 자동으로 재계산됩니다.

데이터 시스템 수준에서 우리가 원하는 것도 정확히 이것입니다. 레코드가 바뀌면 그 인덱스가 자동으로 갱신되고, 그에 의존하는 캐시된 뷰와 집계가 자동으로 새로 고쳐지기를 — 그리고 어떻게 그렇게 되는지 신경 쓰지 않고 그냥 올바르게 동작한다고 믿을 수 있기를.

스프레드시트와 다른 점은 오늘날의 데이터 시스템이 결함 감내적이고, 확장 가능하고, 내구성 있게 저장해야 한다는 것입니다. 또한 다른 사람들이 다른 시기에 만든 이종 기술을 통합하고 기존 라이브러리·서비스를 활용해야 합니다. 모든 소프트웨어가 하나의 언어·프레임워크·도구로 개발되기를 기대하는 것은 비현실적입니다.
13.2 파생 함수로서의 애플리케이션 코드

어떤 파생은 내장 기능, 어떤 파생은 우리 코드

보조 인덱스

가장 단순한 변환 함수. 각 행/문서에서 인덱싱 대상 값을 뽑아 정렬합니다.

CREATE INDEX로 호출 가능한 내장 기능.

전문 검색 인덱스

언어 감지, 단어 분절, 어간 추출, 철자 교정, 동의어 식별을 거쳐 역색인을 만듭니다.

기본 기능은 내장, 정교한 기능은 도메인 튜닝 필요.

ML 모델

특징 추출과 통계 분석으로 학습 데이터에서 파생됩니다. 새 입력에 적용된 출력은 입력과 학습된 파라미터에서 파생됩니다.

특징 공학은 악명 높게 애플리케이션 특수적.

캐시

UI에 표시될 형태로의 집계를 담습니다. 채우려면 UI가 어떤 필드를 참조하는지 알아야 하고, UI가 바뀌면 정의를 갱신하고 캐시를 재구축해야 합니다.

파생 함수가 보조 인덱스처럼 정형화된 함수가 아닐 때는 애플리케이션 특수적 커스텀 코드가 필요합니다 — 그리고 여기서 많은 데이터베이스가 고전합니다. 관계형 DB는 트리거, 저장 프로시저, UDF를 지원하지만, 이들은 데이터베이스 설계에서 다소 뒷전이었습니다.
13.2 코드와 상태의 분리

"우리는 교회와 국가의 분리를 믿습니다"

이론적으로 데이터베이스는 운영체제처럼 임의의 애플리케이션 코드를 위한 배포 환경이 될 수 있습니다. 그러나 실제로는 부적합했습니다 — 의존성·패키지 관리, 버전 관리, 롤링 업그레이드, 진화성, 모니터링, 메트릭, 네트워크 서비스 호출, 외부 시스템 통합 같은 현대 애플리케이션 개발의 요구에 잘 맞지 않기 때문입니다.

반면 Kubernetes, Docker, Mesos, YARN 같은 배포·클러스터 관리 도구는 애플리케이션 코드 실행을 위해 특별히 설계되었고, 한 가지에 집중함으로써 UDF 실행을 여러 기능 중 하나로 제공하는 DB보다 훨씬 잘 해냅니다.

그래서 추세는 무상태 애플리케이션 로직과 상태 관리(데이터베이스)를 분리하는 것입니다 — 애플리케이션 로직을 DB에 넣지 않고, 영속 상태를 애플리케이션에 넣지 않기.

농담 해설

여기서 Church는 람다 계산법을 만든 수학자 알론조 처치를 가리킵니다. 람다 계산법에는 가변 상태가 없으므로(덮어쓸 수 있는 변수가 없음), 가변 상태는 처치의 작업과 분리되어 있다고 말할 수 있죠.

이 전형적인 모델에서 데이터베이스는 네트워크를 통해 동기적으로 접근되는 가변 공유 변수처럼 작동합니다. 애플리케이션은 읽고 갱신하며, DB는 내구성·동시성 제어·결함 감내를 돌봅니다.
그런데 대부분의 언어에서 가변 변수의 변경을 구독할 수 없습니다 — 주기적으로 읽을 수만 있죠. 스프레드시트와 달리 값이 바뀌어도 알림이 오지 않습니다. (직접 구현하면 옵서버 패턴이지만, 대개 언어 내장 기능이 아닙니다.)
데이터베이스는 이 수동적(passive) 태도를 물려받았습니다. 내용이 변했는지 알려면 폴링밖에 없는 경우가 많고, 변경 구독은 이제서야 등장하기 시작한 기능입니다.
13.2 데이터플로 · 상태 변경과 코드의 상호작용

수동적 변수에서 능동적 협업으로

데이터플로 관점은 애플리케이션 코드와 상태 관리의 관계를 재협상합니다. 데이터베이스를 애플리케이션이 조작하는 수동적 변수로 다루는 대신, 상태 · 상태 변경 · 그것을 처리하는 코드의 상호작용과 협업을 훨씬 많이 생각합니다. 애플리케이션 코드는 한 곳의 상태 변경에 반응해 다른 곳의 상태 변경을 촉발합니다.

이 아이디어는 이미 CDC, 액터 모델, 트리거, 증분 뷰 유지에서 보았습니다. DB를 언번들링한다는 것은 이를 주 데이터베이스 외부의 파생 데이터셋 생성(캐시, 전문 검색 인덱스, ML, 분석 시스템)에 적용하는 것입니다.

파생 데이터 유지에 필요한 속성

  • 순서 — 여러 뷰가 하나의 이벤트 로그에서 파생되면, 서로 일관되려면 같은 순서로 이벤트를 처리해야 합니다.
  • 결함 감내 — 메시지 단 하나만 잃어도 파생 데이터셋은 원본과 영구히 어긋납니다. 메시지 전달과 파생 상태 갱신 모두 신뢰성 있어야 합니다.
안정적 메시지 순서와 결함 감내 처리는 까다로운 요구지만, 분산 트랜잭션보다 훨씬 저렴하고 운영상 견고합니다. 현대 스트림 프로세서는 이를 대규모로 제공하며, 애플리케이션 코드를 스트림 연산자로 실행하게 해줍니다.
파이프로 연결된 Unix 도구처럼, 스트림 연산자를 조합해 데이터플로 중심의 큰 시스템을 만들 수 있습니다. 각 연산자는 상태 변경 스트림을 입력받아 다른 상태 변경 스트림을 출력합니다.
13.2 스트림 프로세서와 서비스

가장 빠르고 신뢰할 수 있는 네트워크 요청은, 요청하지 않는 것

환율이 다른 통화로 결제되는 구매를 처리한다고 해봅시다. 통화 변환에는 현재 환율이 필요합니다. 두 가지 구현이 있습니다.

실험 · 마이크로서비스(RPC) vs 데이터플로(스트림 조인)
두 방식을 실행해 비교해 보세요.
단, 이 조인은 시간 의존적입니다. 나중에 구매 이벤트를 재처리하면 환율은 이미 바뀌어 있습니다. 원래 출력을 재구성하려면 구매 시점의 과거 환율을 얻어야 합니다. 서비스를 질의하든 스트림을 구독하든 이 시간 의존성은 다뤄야 합니다.
13.2 파생 상태 관찰하기

쓰기 경로와 읽기 경로 — 그 경계를 움직여보기

데이터가 쓰일 때마다 여러 배치·스트림 단계를 거쳐 파생 데이터셋이 갱신되는 것이 쓰기 경로(사전 계산, 즉시 실행 = eager). 사용자 요청을 처리할 때 파생 데이터셋에서 읽어 응답을 구성하는 것이 읽기 경로(요청 시에만 = lazy). 파생 데이터셋은 두 경로가 만나는 지점입니다.

그림 13-1 — 검색 인덱스에서 쓰기(문서 갱신)와 읽기(질의)가 만난다. 캐시·인덱스·구체화 뷰의 역할은 단순하다: 읽기 경로와 쓰기 경로의 경계를 옮기는 것. 사전 계산으로 쓰기에 더 많은 일을 시켜 읽기의 수고를 아낀다. (2장 소셜 네트워크 홈 타임라인 사례가 바로 이 이야기였습니다 — 500쪽을 돌아 제자리로!)

13.2 구체화 뷰와 캐싱

인덱스만이 유일한 경계는 아니다

인덱스 없음

쓰기 경로는 할 일이 없습니다(갱신할 인덱스가 없음). 대신 검색 질의는 모든 문서를 스캔해야 하고(grep처럼), 문서가 많아지면 매우 비쌉니다.

인덱스

양쪽 모두 일을 합니다. 쓰기는 문서에 나오는 모든 항의 인덱스 항목을 갱신하고, 읽기는 질의의 각 단어를 찾아 불리언 로직(AND / OR + 동의어)을 적용합니다.

모든 결과 사전 계산

읽기 경로는 거의 공짜(불리언 로직 없이 결과 반환)지만 쓰기 경로가 극도로 비쌉니다. 가능한 질의 집합은 무한(적어도 항 수에 지수적)하므로 실현 불가능합니다.

현실적 선택은 가장 흔한 질의만 사전 계산해 인덱스를 거치지 않고 빠르게 제공하고, 드문 질의는 인덱스에서 처리하는 것입니다. 이것을 흔한 질의의 캐시라 부르지만, 그 결과에 포함될 새 문서가 생기면 갱신해야 하므로 구체화 뷰라고 불러도 됩니다.
13.2 상태를 가진 오프라인 클라이언트

화면의 픽셀은 모델 객체의 구체화 뷰다

과거 웹 브라우저는 인터넷이 연결돼야만 유용한 무상태 클라이언트였습니다(오프라인에서 할 수 있는 건 이미 로드된 페이지를 스크롤하는 정도). 그러나 이제 단일 페이지 JS 앱은 클라이언트 측 UI 상호작용과 영속 로컬 저장소를 갖고, 모바일 앱도 기기에 많은 상태를 저장해 대부분의 상호작용에 서버 왕복이 필요 없습니다.

영속 로컬 상태는 사용자가 오프라인에서 작업하고 연결이 되면 배경에서 동기화하는 애플리케이션 부류를 가능하게 합니다. 셀룰러 연결이 느리고 불안정할 때, UI가 동기 네트워크 요청을 기다리지 않고 앱이 대체로 오프라인에서 동작한다는 것은 큰 이점입니다.

관점의 전환

기기의 상태를 서버 상태의 캐시로 생각할 수 있습니다.

화면의 픽셀은 클라이언트 앱 모델 객체의 구체화 뷰이고, 모델 객체는 원격 데이터센터 상태의 로컬 복제본입니다.

중앙 DB와 대화하는 무상태 클라이언트라는 가정에서 벗어나면 새로운 가능성의 세계가 열립니다.

13.2 클라이언트로 상태 변경 밀어내기

쓰기 경로를 최종 사용자까지 연장하기

일반적인 웹 페이지는 서버에서 데이터가 바뀌어도 새로 고침할 때까지 알지 못합니다. 브라우저는 데이터를 한 시점에만 읽고 정적이라 가정하며, 업데이트를 구독하지 않습니다. 즉 브라우저의 상태는 명시적으로 폴링하지 않으면 갱신되지 않는 오래된 캐시입니다. (RSS 같은 HTTP 기반 피드 구독 프로토콜도 사실 기본적인 폴링입니다.)

최근 프로토콜은 요청/응답 패턴을 넘어섰습니다. 서버 전송 이벤트(EventSource API)와 WebSocket은 브라우저가 TCP 연결을 열어두고 서버가 능동적으로 메시지를 밀어낼 수 있게 합니다 — 클라이언트 측 상태의 낡음(staleness)을 줄일 기회입니다.

쓰기 경로 / 읽기 경로 모델로 보면, 상태 변경을 클라이언트 기기까지 능동적으로 밀어내는 것은 쓰기 경로를 최종 사용자까지 연장하는 것입니다. 클라이언트는 최초 초기화 때 읽기 경로로 초기 상태를 얻고, 그 뒤로는 서버가 보내는 상태 변경 스트림에 의존할 수 있습니다.
스트림 처리와 메시징의 아이디어는 데이터센터 안에만 국한되지 않습니다. 최종 사용자 기기까지 끝까지 밀고 나갈 수 있습니다.
기기는 종종 오프라인이 되어 알림을 받지 못하지만, 이미 해결한 문제입니다 — 로그 기반 브로커의 소비자가 재연결 후 끊긴 동안 도착한 메시지를 놓치지 않는 방법(소비자 오프셋)이 그것입니다. 같은 기법이 개인 사용자에게도 통합니다. 각 기기는 작은 이벤트 스트림의 작은 구독자입니다.
13.2 종단간 이벤트 스트림

왜 모든 애플리케이션을 이렇게 만들지 않는가?

React나 Elm 같은 상태 있는 클라이언트·UI 도구는 이미 기반 상태 변화에 따라 렌더링을 갱신하는 능력이 있습니다. 서버가 상태 변경 이벤트를 이 클라이언트 측 파이프라인에 밀어넣게 확장하는 것은 매우 자연스럽습니다.

그러면 상태 변경이 종단간 쓰기 경로를 따라 흐를 수 있습니다 — 한 기기의 상호작용 → 이벤트 로그 → 여러 파생 데이터 시스템과 스트림 프로세서 → 다른 기기의 사용자 인터페이스. 지연은 꽤 낮게, 종단간 1초 이내도 가능합니다.

인스턴트 메시징과 온라인 게임 같은 일부 애플리케이션은 이미 이런 "실시간" 아키텍처를 갖고 있습니다(응답 시간 보장이 아니라 낮은 지연의 상호작용이라는 의미에서).

문제는 무상태 클라이언트와 요청/응답이라는 가정이 우리의 데이터베이스, 라이브러리, 프레임워크, 프로토콜에 깊이 뿌리박혀 있다는 점입니다. 많은 데이터 저장소는 요청 하나에 응답 하나를 반환하는 연산을 지원하지만, 시간에 걸쳐 응답 스트림을 반환하는 연산(변경 구독)을 지원하는 것은 훨씬 적습니다.
쓰기 경로를 최종 사용자까지 연장하려면 요청/응답에서 발행/구독 데이터플로로 옮겨가며 이 시스템들을 근본적으로 다시 생각해야 합니다. 노력이 필요하지만, 더 반응적인 UI와 더 나은 오프라인 지원이라는 이점이 있습니다.
13.2 읽기도 이벤트다

요청을 처리하는 것과 조인을 수행하는 것은 사실 같은 일이다

지금까지의 모델에서 저장소로의 쓰기는 이벤트 로그를 거치고, 읽기는 데이터를 가진 노드로 가는 일시적 네트워크 요청이었습니다. 합리적인 설계지만 유일한 설계는 아닙니다.

읽기 요청도 이벤트 스트림으로 표현해서 읽기 이벤트와 쓰기 이벤트를 같은 스트림 프로세서로 보낼 수 있습니다. 프로세서는 읽기 이벤트에 대해 결과를 출력 스트림으로 내보내며 응답합니다.

스트림 프로세서도 집계와 조인을 위해 상태를 유지해야 하는데, 보통 내부에 숨겨진 이 상태를 외부 클라이언트가 질의할 수 있게 하는 프레임워크도 있습니다 — 스트림 프로세서 자체가 일종의 단순한 데이터베이스가 되는 것이죠.

쓰기와 읽기가 모두 이벤트가 되어 같은 연산자로 라우팅되면, 우리는 사실 읽기 질의 스트림과 데이터베이스 사이의 스트림-테이블 조인을 수행하고 있는 것입니다. 각 읽기 이벤트는 관련 데이터를 가진 샤드로 보내져야 합니다 — 배치·스트림 프로세서가 조인 시 같은 키로 코파티션하는 것과 똑같습니다.
이 대응은 꽤 근본적입니다. 일회성 읽기는 조인 연산자를 통과한 뒤 즉시 잊히고, 구독 요청은 조인의 반대편에 있는 과거·미래 이벤트와의 지속적인 조인입니다.
읽기 이벤트 로그를 남기면 인과 의존성과 데이터 계보(provenance) 추적에도 이점이 있습니다. 온라인 상점에서 고객에게 보여준 예상 배송일과 재고 상태가 구매 결정에 영향을 줬다면, 그 질의 결과를 기록해야 그 연결을 분석할 수 있습니다.
대신 저장·I/O 비용이 추가됩니다. 오버헤드를 줄이는 최적화는 여전히 열린 연구 문제지만, 운영 목적으로 이미 읽기 요청을 로깅한다면 그 로그를 요청의 원천으로 삼는 것은 큰 변화가 아닙니다.
13.2 다중 샤드 데이터 처리

여러 샤드를 결합하는 복잡한 질의의 분산 실행

단일 샤드만 건드리는 질의라면 스트림으로 보내 응답 스트림을 모으는 수고는 과잉일 수 있습니다. 그러나 이 아이디어는 스트림 프로세서가 이미 제공하는 메시지 라우팅·샤딩·조인 인프라를 활용해, 여러 샤드의 데이터를 결합하는 복잡한 질의를 분산 실행할 가능성을 엽니다.

Storm의 분산 RPC 기능이 이 패턴을 지원합니다. 예를 들어 소셜 네트워크에서 어떤 URL을 본 사람 수(그 URL을 올린 모든 이의 팔로워 집합의 합집합)를 계산하는 데 쓰였습니다. 사용자 집합이 샤딩되어 있으니 여러 샤드의 결과를 결합해야 합니다.

사기 방지

구매 이벤트가 사기인지 평가하려면 사용자의 IP 주소, 이메일, 청구지, 배송지 등의 평판 점수를 살펴봐야 합니다. 각 평판 데이터베이스가 제각기 샤딩되어 있으니, 한 구매 이벤트의 점수를 모으려면 서로 다르게 샤딩된 데이터셋과의 연속적인 조인이 필요합니다.

데이터 웨어하우스 질의 엔진의 내부 실행 그래프도 비슷한 특성을 가집니다. 이런 다중 샤드 조인이 필요하다면 그 기능을 제공하는 데이터베이스를 쓰는 편이 스트림 프로세서로 구현하는 것보다 대개 간단합니다.
그러나 질의를 스트림으로 다루는 것은, 통상적인 기성 솔루션의 한계에 부딪히는 대규모 애플리케이션을 구현할 하나의 선택지를 제공합니다.

13.3 우리의 기반은 생각보다 약하다

중요한 주제인데, 이해와 방법론이 놀랄 만큼 허술하다

약 40년간 원자성·격리성·내구성이 올바른 애플리케이션을 만드는 선택 도구였습니다. 그러나 그 기반은 보이는 것보다 약합니다 — 약한 격리 수준의 혼란이 그 증거입니다.

어떤 영역에서는 트랜잭션이 아예 버려지고 성능·확장성은 좋지만 의미론이 지저분한 모델로 대체되었습니다. 일관성은 자주 이야기되지만 잘 정의되지 않습니다. 어떤 이들은 가용성을 위해 "약한 일관성을 받아들이라"고 주장하지만, 그것이 실무에서 무엇을 뜻하는지에 대한 명확한 그림은 없습니다.

예를 들어 특정 애플리케이션을 특정 격리 수준이나 복제 구성으로 돌리는 것이 안전한지 판단하기가 매우 어렵습니다. 동시성이 낮고 결함이 없을 때는 잘 동작하는 듯 보이지만, 까다로운 상황에서 미묘한 버그가 드러나곤 합니다.

카일 킹스버리의 Jepsen 실험은 일부 제품이 주장하는 안전성 보장과 네트워크 문제·크래시 상황에서의 실제 동작 사이의 뚜렷한 불일치를 드러냈습니다.
인프라 제품에 문제가 없더라도 애플리케이션 코드가 기능을 올바르게 써야 하는데, 설정이 이해하기 어렵다면(약한 격리 수준, 쿼럼 구성 등) 오류가 나기 쉽습니다.
간혹 데이터가 손상·손실돼도 괜찮은 애플리케이션이라면 인생이 훨씬 단순합니다. 더 강한 보장이 필요하다면 직렬성과 원자적 커밋이 확립된 접근이지만 비용이 따릅니다 — 보통 단일 데이터센터에서만 동작하고(지리적 분산 배제), 달성 가능한 규모와 결함 감내 특성을 제한합니다.
전통적 트랜잭션 접근이 사라지는 것은 아니지만, 마지막 정답도 아닙니다. 이 절에서는 데이터플로 아키텍처 맥락에서 정확성을 다르게 생각하는 방법을 탐구합니다.
13.3 연산의 정확히 한 번 실행

포기하면 데이터 손실, 재시도하면 중복

애플리케이션이 직렬성 트랜잭션처럼 비교적 강한 안전 속성을 제공하는 데이터 시스템을 쓴다고 해서, 데이터 손실이나 손상이 없다고 보장되지는 않습니다. 애플리케이션 버그가 잘못된 데이터를 쓰거나 지운다면 직렬성 트랜잭션은 구해주지 못합니다.

이는 불변·추가 전용 데이터를 지지하는 논거입니다. 결함 있는 코드가 좋은 데이터를 파괴할 능력을 제거하면 실수에서 회복하기가 훨씬 쉽습니다. 다만 불변성만으로 만병통치는 아닙니다.

메시지 처리 중 문제가 생기면 ① 포기(메시지를 버리고 데이터 손실을 감수)하거나 ② 재시도할 수 있습니다. 재시도하면 사실 첫 시도가 성공했는데 확인만 못 받은 경우가 있어 두 번 처리될 위험이 있습니다.

두 번 처리는 데이터 손상의 한 형태입니다 — 같은 서비스에 두 번 청구하거나 카운터를 두 번 증가(지표 과대 계상)시키는 것은 바람직하지 않습니다.
여기서 정확히 한 번이란, 결함으로 재시도되었더라도 최종 효과가 결함이 없었던 것과 같도록 계산을 배치하는 것입니다.
가장 효과적인 접근 하나는 연산을 멱등(idempotent)하게 만드는 것 — 한 번 실행되든 여러 번 실행되든 같은 효과를 갖게 하는 것입니다.
그러나 자연적으로 멱등이 아닌 연산에 이를 적용하려면 노력과 주의가 필요합니다. 추가 메타데이터(값을 갱신한 연산 ID 집합 등)를 유지해야 하고, 노드 페일오버 시 펜싱을 보장해야 합니다.
13.3 중복 억제

TCP도, 트랜잭션도, 이 중복은 막지 못한다

실험 · 사용자가 폼을 다시 제출하면 어디까지 막히는가
‘다음 단계’를 눌러 진행하세요.

TCP는 시퀀스 번호로 패킷 순서를 잡고 손실·중복을 판단해, 애플리케이션에 넘기기 전에 중복을 제거합니다. 그러나 이 중복 억제는 단일 TCP 연결 안에서만 유효합니다. 많은 DB에서 트랜잭션은 클라이언트 연결에 묶여 있으므로, COMMIT을 보낸 뒤 응답을 듣기 전에 연결이 끊기면 클라이언트는 커밋됐는지 중단됐는지 알 수 없습니다.

13.3 요청을 고유하게 식별하기

재연결해서 재시도하면 $11 대신 $22가 이동한다

예제 13-1 · 멱등이 아닌 송금

BEGIN TRANSACTION;
UPDATE accounts SET balance = balance + 11.00
  WHERE account_id = 1234;
UPDATE accounts SET balance = balance - 11.00
  WHERE account_id = 4321;
COMMIT;
트랜잭션 원자성의 표준 예제이지만 올바르지 않습니다. 재시도하면 TCP 중복 억제의 범위를 벗어나며, 멱등이 아니므로 $22가 이동할 수 있습니다. 실제 은행은 이렇게 동작하지 않습니다.
2PC는 TCP 연결과 트랜잭션의 1:1 대응을 깨뜨리지만(코디네이터가 재연결해 커밋/중단을 알림), 그것으로 한 번만 실행이 보장되지는 않습니다. 최종 사용자 기기와 애플리케이션 서버 사이의 네트워크가 여전히 남아 있기 때문입니다.

예제 13-2 · 고유 ID로 중복 요청 억제

ALTER TABLE requests ADD UNIQUE (request_id);
BEGIN TRANSACTION;
INSERT INTO requests
  (request_id, from_account, to_account, amount)
VALUES('0286FDB8-D7E1-423F-B40B-792B3608036C',
       4321, 1234, 11.00);
UPDATE accounts SET balance = balance + 11.00
  WHERE account_id = 1234;
UPDATE accounts SET balance = balance - 11.00
  WHERE account_id = 4321;
COMMIT;
요청마다 고유 식별자(UUID)를 만들어 숨은 폼 필드로 넣거나 폼 필드들의 해시로 도출하면, 두 번 제출된 요청은 같은 request ID를 갖습니다. 그 ID를 데이터베이스까지 끝까지 전달해 같은 ID의 요청을 하나만 실행하게 합니다.
이 코드는 request_id의 고유성 제약에 의존합니다. 관계형 DB는 약한 격리 수준에서도 고유성 제약을 대체로 올바르게 유지합니다(애플리케이션 수준 check-then-insert는 비직렬 격리에서 실패할 수 있는 것과 대조적).
덧붙여 requests 테이블은 일종의 이벤트 로그 역할을 합니다. 잔액 갱신은 같은 트랜잭션에 있을 필요가 없습니다 — 이벤트가 정확히 한 번 처리되기만 하면(다시 request ID로 강제) 다운스트림 소비자가 파생할 수 있습니다.
13.3 종단간 논증

낮은 계층의 신뢰성만으로는 종단간 정확성이 보장되지 않는다

문제의 그 기능은, 통신 시스템의 양 끝단에 서 있는 애플리케이션의 지식과 도움이 있어야만 완전하고 올바르게 구현될 수 있다. 따라서 그 기능을 통신 시스템 자체의 기능으로 제공하는 것은 불가능하다. — 솔처, 리드, 클라크 (1984)

중복 억제

TCP는 연결 수준에서, 일부 스트림 프로세서는 메시지 처리 수준에서 중복을 억제합니다. 그러나 첫 요청이 타임아웃된 사용자의 재제출은 막지 못합니다. 해법은 최종 사용자 클라이언트에서 DB까지 전달되는 트랜잭션 식별자입니다.

무결성 검사

이더넷·TCP·TLS의 체크섬은 네트워크상의 패킷 손상을 잡지만, 양 끝단 소프트웨어 버그로 인한 손상이나 디스크상의 손상은 잡지 못합니다. 모든 원천을 잡으려면 종단간 체크섬이 필요합니다.

암호화

집 WiFi 비밀번호는 WiFi 트래픽 도청을 막지만 인터넷상의 공격자는 막지 못하고, TLS/SSL은 네트워크 공격자를 막지만 서버 침해는 막지 못합니다. 종단간 암호화·인증만이 모두를 막습니다.

저수준 기능(TCP 중복 억제, 이더넷 체크섬, WiFi 암호화)은 그 자체로 종단간 속성을 제공하지 못해도 여전히 유용합니다 — 상위 계층의 문제 확률을 낮추기 때문입니다. TCP가 패킷 순서를 바로잡지 않는다면 HTTP 요청은 자주 뒤엉킬 것입니다.
그러나 결함 감내 메커니즘은 제대로 만들기 어렵습니다. 트랜잭션은 넓은 범위의 문제를 커밋 또는 중단 둘로 축약하는 유용한 추상화지만 충분하지 않고, 특히 이종 저장 기술이 얽히면 비쌉니다. 너무 비싸서 분산 트랜잭션을 거부하면 애플리케이션 코드에서 결함 감내를 재구현하게 되고, 대개 올바르게 동작하지 않아 결국 데이터 손실·손상으로 이어집니다.
13.3 제약 조건 강제

고유성 제약은 합의를 요구한다

사용자명·이메일은 사용자를 고유하게 식별해야 하고, 파일 저장 서비스는 같은 이름의 파일을 둘 가질 수 없으며, 두 사람이 같은 좌석을 예약할 수 없습니다. 비슷한 제약들 — 계좌 잔액이 음수가 되지 않게, 재고보다 많이 팔지 않게, 회의실 예약이 겹치지 않게 — 도 같은 기법으로 다룰 수 있습니다.

분산 환경에서 고유성 제약을 강제하려면 합의가 필요합니다. 동일한 값의 동시 요청이 여러 개 오면, 시스템은 어느 하나를 받아들이고 나머지를 위반으로 거부해야 합니다.

가장 흔한 방법은 단일 노드를 리더로 삼아 모든 결정을 맡기는 것입니다. 모든 요청을 한 노드로 몰아도 괜찮고 그 노드가 죽지 않는 한 잘 동작합니다. Raft 같은 합의 알고리즘은 리더가 죽었을 때(또는 죽은 것으로 믿어질 때) 안전하게 새 리더를 뽑고 스플릿 브레인을 막는 문제를 다룹니다.

확장 방법 — 고유해야 하는 값으로 샤딩하면 됩니다. request ID로 고유성이 필요하면 같은 ID의 요청이 같은 샤드로 가게, 사용자명이 고유해야 하면 사용자명 해시로 샤딩합니다.
그러나 비동기 다중 리더 복제는 배제됩니다. 서로 다른 리더가 충돌하는 쓰기를 동시에 받아들일 수 있어 값이 더는 고유하지 않게 됩니다. 제약을 위반하는 쓰기를 즉시 거부하려면 동기적 코디네이션은 불가피합니다.
13.3 로그 기반 메시징에서의 고유성

단일 스레드가 로그를 순차로 읽으면, 누가 먼저였는지 명확해진다

실험 · 세 사용자가 같은 사용자명을 동시에 요청한다
버튼을 눌러 실행하세요.
  • 사용자명 요청마다 메시지로 인코딩해 사용자명 해시로 정해진 샤드에 추가한다
  • 스트림 프로세서가 로그를 순차적으로 읽으며, 로컬 DB로 선점된 이름을 추적한다. 사용 가능하면 점유 기록 후 성공 메시지를, 이미 선점되었으면 거부 메시지를 출력 스트림에 내보낸다
  • 클라이언트는 출력 스트림을 지켜보며 자기 요청에 대응하는 성공/거부를 기다린다
공유 로그는 모든 소비자가 같은 순서로 메시지를 보게 합니다(전체 순서 브로드캐스트 = 합의). 이 알고리즘은 사실 공유 로그로 합의를 달성하는 구성과 동일하며, 샤드 수를 늘려 큰 처리량으로 쉽게 확장됩니다.
근본 원리는 충돌할 수 있는 쓰기를 같은 샤드로 라우팅해 순차 처리하는 것입니다. 충돌의 정의는 애플리케이션에 따라 다를 수 있고, 스트림 프로세서는 임의의 로직으로 요청을 검증할 수 있습니다.

전통적 방식이라면 세 샤드(요청 ID · 지급인 계좌 · 수취인 계좌)에 걸친 원자적 커밋이 필요하고, 그러면 해당 샤드들의 다른 모든 트랜잭션과 전체 순서를 이루게 되어 처리량이 떨어집니다. 세 계좌가 같은 샤드에 있어도 무관합니다 — 요구 조건은 두 가지뿐: 계좌별 이벤트가 로그 순서대로 최소 한 번 처리되고, 스트림 프로세서가 결정론적일 것.

13.3 원자성의 출처

원자성은 트랜잭션이 아니라, "첫 이벤트를 로그에 쓰는 행위"에서 온다

지급인 계좌 프로세서가 결제 요청 처리 중 크래시하면? 출력 메시지가 나갔을 수도, 안 나갔을 수도 있습니다. 복구 후 프로세서는 (최소 한 번 의미 때문에) 같은 요청을 다시 처리하고, (결정론적이므로) 같은 결정을 내립니다. 따라서 같은 request ID의 같은 출력 메시지를 다시 내보내며, 중복이면 다운스트림 소비자가 request ID로 무시합니다.

이 시스템의 원자성은 트랜잭션이 아니라, 최초 요청 이벤트를 지급인 계좌 로그에 쓰는 것이 원자적 행위라는 사실에서 나옵니다. 그 하나의 이벤트가 로그에 들어가면, 모든 다운스트림 이벤트는 결국 쓰이게 됩니다 — 크래시 복구 후일 수도, 중복이 있을 수도 있지만 결국 나타납니다.
정확히 한 번 의미가 있으면 구현이 더 쉬워집니다. 스트림 프로세서의 로컬 상태가 처리한 메시지 집합과 일관됨을 보장하므로, 크래시 후 재처리 시 로컬 상태도 그 이전 상태로 되돌아갑니다.
사용자가 이체 승인 여부를 알고 싶다면 지급인 계좌 로그 샤드를 구독해 outgoing payment 이벤트를 기다리면 됩니다. 잔액 부족을 명시적으로 알리려면 프로세서가 "결제 거절" 이벤트를 그 샤드에 내보내면 됩니다.
다중 샤드 트랜잭션을 서로 다르게 샤딩된 여러 단계로 쪼개고 종단간 request ID를 쓰면, 원자적 커밋 프로토콜 없이도 결함 속에서 같은 정확성 속성(모든 요청이 지급인·수취인 양쪽에 정확히 한 번 적용)을 얻습니다.
13.3 적시성과 무결성

"일관성"은 사실 두 가지 요구를 뒤섞은 말이다

적시성 timeliness

사용자가 시스템을 최신 상태로 관찰하도록 보장하는 것. 오래된 사본을 읽으면 일관되지 않은 상태를 볼 수 있지만, 그 불일치는 일시적이며 기다렸다 다시 시도하면 해소됩니다.

CAP 정리의 "일관성"은 선형성을 뜻하며, 적시성을 달성하는 강한 방법입니다. 쓰기 후 읽기 일관성처럼 더 약한 적시성도 유용합니다.

무결성 integrity

손상이 없음 — 데이터 손실도, 모순되거나 거짓된 데이터도 없는 상태. 파생 데이터셋이 기반 데이터의 뷰로 유지된다면 그 파생이 올바라야 합니다. 레코드가 빠진 인덱스는 쓸모없습니다.

무결성이 위반되면 불일치는 영구적입니다. 기다려도 고쳐지지 않고 명시적 검사와 수리가 필요합니다. ACID의 "일관성"은 보통 애플리케이션 특수적인 무결성을 뜻하며, 원자성과 내구성이 이를 보존하는 중요한 도구입니다.

슬로건으로: 결과적 일관성 아래에서 적시성 위반은 허용되지만, 무결성 위반은 영구적 불일치를 낳는다. 대부분의 애플리케이션에서 무결성이 적시성보다 훨씬 중요합니다. 적시성 위반은 짜증나고 혼란스럽지만, 무결성 위반은 파국적입니다.

신용카드 명세서에 지난 24시간의 거래가 아직 안 보이는 것은 놀랍지 않습니다 — 은행은 비동기로 정산하며 여기서 적시성은 중요하지 않습니다. 그러나 명세서 잔액이 거래 합계 + 이전 잔액과 다르거나(합산 오류), 고객에게 청구됐는데 판매자에게 지급되지 않았다면(돈이 사라짐) 매우 나쁩니다 — 이것이 무결성 위반입니다.

13.3 데이터플로 시스템의 정확성

적시성과 무결성을 분리하다

ACID 트랜잭션은 보통 적시성(선형성)과 무결성(원자적 커밋)을 둘 다 제공합니다. 그래서 ACID 관점에서 정확성에 접근하면 둘의 구별은 별로 중요하지 않습니다.

반면 이 장의 이벤트 기반 데이터플로 시스템의 흥미로운 성질은 적시성과 무결성을 분리(decouple)한다는 점입니다. 비동기 처리에서는 명시적으로 기다리는 소비자를 만들지 않는 한 적시성 보장이 없습니다 — 사용자가 결제를 요청하고 프로세서가 처리하기 전에 계좌를 읽으면 그 결제를 못 볼 수 있습니다.

그러나 무결성은 스트리밍 시스템의 핵심입니다. 정확히 한 번(또는 실질적 한 번) 의미가 바로 무결성 보존 메커니즘입니다. 이벤트가 손실되거나 두 번 효력을 내면 무결성이 깨질 수 있으니, 결함 감내 메시지 전달과 중복 억제가 중요합니다.

무결성을 달성한 네 가지 메커니즘

  • 단일 메시지로 표현 — 쓰기 연산의 내용을 하나의 메시지로 표현해 원자적으로 쉽게 기록합니다. 이벤트 소싱과 매우 잘 맞습니다.
  • 결정론적 파생 — 다른 모든 상태 갱신을 그 단일 메시지에서 결정론적 파생 함수로 도출합니다(저장 프로시저와 유사).
  • 클라이언트 생성 request ID — 모든 처리 계층을 통과시켜 종단간 중복 억제와 멱등성을 가능하게 합니다.
  • 불변 메시지 + 재처리 — 메시지를 불변으로 만들고 파생 데이터를 때때로 재처리할 수 있게 하여 버그로부터의 회복을 쉽게 합니다.
신뢰성 있는 스트림 처리는 분산 트랜잭션과 원자적 커밋 없이 무결성을 보존할 수 있고, 따라서 비슷한 정확성을 훨씬 나은 성능과 운영 견고성으로 달성할 잠재력이 있습니다.
13.3 느슨하게 해석된 제약 조건

많은 비즈니스는 "하드 제약"의 위반을 이미 허용한다

  • 재고 초과 주문 — 더 주문해 들이고, 지연을 사과하고, 할인을 제공하면 됩니다. 지게차가 창고 물건을 밟았을 때 해야 할 일과 똑같습니다. 사과 워크플로는 이미 비즈니스 프로세스의 일부이므로, 재고 수량에 대한 하드 제약은 불필요할 수 있습니다.
  • 초과 예약 — 항공사는 일부 승객이 못 탈 것을 기대해 초과 예약하고, 호텔도 취소를 기대해 초과 예약합니다. "좌석당 한 명" 제약을 비즈니스 이유로 의도적으로 위반하고 보상 절차(환불, 업그레이드, 이웃 호텔 무료 객실)를 둡니다. 초과 예약이 없더라도 기상 결항이나 파업에 대응하려면 사과·보상 절차가 필요합니다.
  • 초과 인출 — 잔액보다 많이 인출하면 은행은 초과 인출 수수료를 부과하고 반환을 요구합니다. 일일 총 인출 한도로 위험을 제한합니다.
  • 조직 간 통합 — 불일치는 필연적으로 발생하고 교정 메커니즘이 필요합니다. 은행 간 결제 정산이 그 예입니다.
실수를 바로잡는 이런 변경을 보상 트랜잭션(compensating transaction)이라 부릅니다. 사과의 비용(돈·평판)은 다양하지만 대개 꽤 낮습니다. 보낸 이메일을 취소할 수는 없어도 정정 메일을 보낼 수 있고, 카드를 두 번 청구했다면 하나를 환불하면 되며 비용은 처리 수수료와 고객 불만 정도입니다.
사과 비용이 수용 가능하다면, 데이터를 쓰기도 전에 모든 제약을 검사하는 전통적 모델은 불필요하게 제한적입니다. 낙관적으로 쓰고 사후에 제약을 검사하는 것이 합리적일 수 있습니다. 회복이 비싼 행동을 하기 전에는 검증하도록 하되, 그것이 쓰기 전에 검증해야 함을 뜻하지는 않습니다.
이런 애플리케이션은 무결성은 필요합니다 — 예약이 사라지거나 대차 불일치로 돈이 사라지는 것은 원하지 않습니다. 그러나 제약 강제의 적시성은 필요하지 않습니다. 재고보다 많이 팔았다면 사후에 수습할 수 있습니다.
13.3 코디네이션 회피 데이터 시스템

사과를 0으로 만들 수는 없다 — 스위트 스팟을 찾는 것

  • 데이터플로 시스템은 원자적 커밋·선형성·동기 크로스 샤드 코디네이션 없이 파생 데이터의 무결성 보장을 유지할 수 있다
  • 엄격한 고유성 제약은 적시성과 코디네이션을 요구하지만, 많은 애플리케이션은 느슨한 제약으로 충분하다 — 일시적으로 위반되고 사후에 고쳐져도, 무결성이 계속 보존된다면
둘을 합치면, 데이터플로 시스템은 코디네이션 없이도 강한 무결성 보장을 주며 많은 애플리케이션의 데이터 관리를 담당할 수 있습니다. 이런 코디네이션 회피 데이터 시스템은 매력적입니다 — 동기적 코디네이션이 필요한 시스템보다 더 나은 성능과 결함 감내를 달성할 수 있습니다.
예컨대 여러 데이터센터에 걸쳐 다중 리더로 운영하며 리전 간 비동기 복제를 할 수 있습니다. 동기 크로스 리전 코디네이션이 필요 없으니 어느 한 DC는 독립적으로 계속 운영됩니다. 적시성 보장은 약하고(코디네이션 없이 선형성은 불가능) 무결성 보장은 강할 수 있습니다.
직렬성 트랜잭션은 파생 상태 유지의 일부로 여전히 유용하지만, 잘 동작하는 작은 범위에서 쓰면 됩니다. XA 같은 이종 분산 트랜잭션은 필요 없습니다. 동기적 코디네이션은 정말 필요한 곳(회복 불가능한 연산 전의 엄격한 제약 강제)에만 도입하면 되고, 애플리케이션의 작은 일부만 필요할 때 전체가 그 비용을 낼 이유는 없습니다.
실험 · 코디네이션을 늘리면 사과가 줄어드는가
슬라이더를 움직여 보세요.

코디네이션과 제약은 불일치에 대한 사과를 줄이지만, 성능과 가용성을 떨어뜨려 장애에 대한 사과를 늘릴 수 있다. 사과를 0으로 만들 수는 없으니, 불일치도 가용성 문제도 너무 많지 않은 스위트 스팟을 겨냥해야 한다.

13.3 신뢰하되 검증하라

시스템 모델은 이진법이 아니라 확률의 문제다

지금까지의 모든 논의는 "어떤 것은 잘못될 수 있지만 다른 것은 그렇지 않다"는 가정 아래 있었습니다 — 이것이 시스템 모델입니다. 프로세스는 크래시할 수 있고, 머신은 갑자기 전원을 잃을 수 있고, 네트워크는 메시지를 임의로 지연·유실할 수 있다고 가정합니다. 동시에 fsync 후 디스크 데이터는 유실되지 않고, 메모리 데이터는 손상되지 않고, CPU 곱셈은 항상 올바르다고 가정합니다.

이런 가정은 대체로 참이며 합리적입니다. 컴퓨터가 실수할까 늘 걱정한다면 아무 일도 못 할 것입니다.

전통적으로 시스템 모델은 결함에 이진적으로 접근합니다 — 어떤 일은 일어날 수 있고 다른 일은 절대 일어나지 않는다고. 현실에서는 확률의 문제입니다. 질문은 우리 가정의 위반이 실제로 마주칠 만큼 자주 일어나는가입니다.

데이터는 메모리에서도, 디스크에서도, 네트워크에서도 손상될 수 있음을 우리는 이미 보았습니다. 어쩌면 이것에 더 주의를 기울여야 하는 것 아닐까요? 충분히 큰 규모에서는 매우 일어나기 어려운 일도 결국 일어납니다.
소프트웨어 버그도 있습니다. 낮은 계층의 체크섬으로는 잡히지 않습니다. 널리 쓰이는 DB에도 버그가 있습니다 — 과거 MySQL은 고유성 제약을 올바르게 유지하지 못한 적이 있고, PostgreSQL의 직렬성 격리 수준은 쓰기 스큐 이상 현상을 보인 적이 있습니다. 견고하고 평판 좋은, 수년간 검증된 DB에서도 그렇습니다. 덜 성숙한 소프트웨어라면 상황은 훨씬 나쁠 것입니다.
애플리케이션 코드에는 훨씬 많은 버그를 가정해야 합니다 — DB 코드만큼의 리뷰와 테스트를 받지 못하니까요. 많은 애플리케이션은 외래 키나 고유성 제약처럼 DB가 제공하는 무결성 보존 기능조차 올바르게 쓰지 않습니다.
ACID의 일관성은 DB가 일관된 상태에서 시작해 트랜잭션이 일관된 상태로 옮긴다는 생각에 기반합니다. 그러나 이는 트랜잭션에 버그가 없다는 가정에서만 의미가 있습니다. 애플리케이션이 (예: 약한 격리 수준을 안전하지 않게 사용해) DB를 잘못 쓰면 무결성은 보장되지 않습니다.
13.3 약속을 맹목적으로 믿지 마라

여전히 있는지 확실히 알고 싶다면, 읽어서 확인해야 한다

하드웨어와 소프트웨어 모두 이상에 부합하지 않으니 데이터 손상은 언젠가 불가피해 보입니다. 그렇다면 최소한 손상 여부를 알아낼 방법은 있어야 합니다 — 고치고 원인을 추적하기 위해서. 데이터 무결성을 검사하는 것을 감사(auditing)라 합니다.

감사는 금융 애플리케이션만의 일이 아닙니다. 다만 금융에서 감사 가능성이 매우 중요한 이유는, 모두가 실수가 일어난다는 것을 알고 문제를 탐지·수정할 필요를 인정하기 때문입니다.

성숙한 시스템은 있을 법하지 않은 일까지 고려해 위험을 관리합니다. HDFS나 Amazon S3 같은 대규모 저장 시스템은 디스크를 완전히 신뢰하지 않습니다. 배경 프로세스가 파일을 계속 다시 읽고 다른 복제본과 비교하며 디스크 간에 옮겨, 조용한 손상(silent corruption)의 위험을 완화합니다.

같은 논리로 백업 복원을 때때로 시도하는 것이 중요합니다. 그러지 않으면 이미 데이터를 잃은 뒤에야 백업이 깨졌음을 알게 됩니다. 다 잘 되고 있다고 맹목적으로 믿지 마세요.
HDFS와 S3도 디스크가 대부분의 시간 올바르게 동작한다고 가정합니다 — 합리적이지만 항상 올바르다는 가정과는 다릅니다. 이런 "신뢰하되 검증하라"식 자기 감사를 하는 시스템은 아직 많지 않습니다. 많은 시스템은 정확성 보장이 절대적이라 가정하고 드문 손상 가능성에 대비하지 않습니다.
미래에는 맹목적 신뢰에 의존하지 않고 자기 무결성을 계속 검사하는 자기 검증·자기 감사 시스템을 더 많이 보게 될지도 모릅니다.
13.3 감사 가능성을 위한 설계

이벤트 기반 시스템은 "왜 그랬는지"를 남긴다

변경 기반 시스템

한 트랜잭션이 여러 객체를 변경하면 근본 이유를 사후에 알기 어렵습니다. 트랜잭션 로그를 잡아둬도, 여러 테이블의 삽입·갱신·삭제만으로는 왜 그 변경이 수행됐는지 명확하지 않습니다.

그 변경을 결정한 애플리케이션 로직의 호출은 일시적이며 재현할 수 없습니다.

이벤트 기반 시스템

이벤트 소싱에서 사용자 입력은 하나의 불변 이벤트로 표현되고 이후의 모든 상태 갱신은 그 이벤트에서 파생됩니다. 파생은 결정론적이고 반복 가능하게 만들 수 있어, 같은 이벤트 로그를 같은 버전의 코드로 돌리면 같은 상태 갱신이 나옵니다.

데이터플로를 명시적으로 만들면 데이터의 계보(provenance)가 훨씬 명확해져 무결성 검사가 실현 가능해집니다.

이벤트 로그는 해시로 저장소가 손상되지 않았음을 검사할 수 있고, 파생 상태는 배치·스트림 프로세서를 다시 돌려 같은 결과가 나오는지 확인하거나 중복 파생을 병렬로 돌릴 수 있습니다.
결정론적이고 잘 정의된 데이터플로는 디버깅과 실행 추적도 쉽게 합니다. 예상치 못한 일이 벌어졌을 때 정확한 정황을 재현할 수 있다는 것은 — 일종의 시간 여행 디버깅 — 큰 가치가 있습니다.
13.3 감사 가능한 데이터 시스템의 도구

종단간 무결성 검사가 오히려 더 빠르게 움직이게 한다

시스템의 모든 개별 컴포넌트가 손상에서 자유롭다고 온전히 믿을 수 없다면, 최소한 주기적으로 데이터 무결성을 검사해야 합니다. 검사하지 않으면 이미 다운스트림 손해를 낸 뒤에야 알게 되고, 그때는 문제 추적이 훨씬 어렵고 비쌉니다.
무결성 검사는 종단간으로 하는 것이 최선입니다. 검사에 더 많은 시스템을 포함할수록 손상이 눈에 띄지 않고 지나갈 기회가 줄어듭니다. 파생 데이터 파이프라인 전체가 종단간으로 올바른지 검사할 수 있다면, 경로상의 모든 디스크·네트워크·서비스·알고리즘이 암묵적으로 검사에 포함됩니다.
지속적 종단간 무결성 검사는 시스템 정확성에 대한 확신을 높여, 결과적으로 더 빠르게 움직일 수 있게 합니다. 자동 테스트처럼 감사는 버그가 빨리 발견될 확률을 높여, 변경이나 새 저장 기술이 손해를 낼 위험을 줄입니다. 변경이 두렵지 않으면 요구사항 변화에 맞춰 애플리케이션을 훨씬 잘 진화시킬 수 있습니다.
현재로선 감사 가능성을 최상위 관심사로 두는 데이터 시스템은 많지 않습니다. 별도 감사 테이블에 변경을 로깅하는 방식도 있지만, 감사 로그와 DB 상태의 무결성을 보장하기는 여전히 어렵습니다. 하드웨어 보안 모듈로 트랜잭션 로그에 주기적으로 서명해 위조 방지는 할 수 있지만, 애초에 올바른 트랜잭션이 로그에 들어갔는지는 보장하지 못합니다.
블록체인(비트코인·이더리움)은 암호학적 일관성 검사를 갖춘 공유 추가 전용 로그입니다. 저장하는 트랜잭션은 이벤트이고, 스마트 컨트랙트는 기본적으로 스트림 프로세서입니다. 합의 프로토콜로 모든 노드가 같은 이벤트 순서에 동의하며, 10장의 합의와 다른 점은 비잔틴 결함 감내라는 것 — 복제본이 서로의 무결성을 계속 검사하므로 일부 노드의 데이터가 손상돼도 동작합니다.
대부분의 애플리케이션에는 블록체인의 오버헤드가 너무 큽니다. 그러나 암호학적 도구는 더 가벼운 맥락에서도 쓸 수 있습니다 — 머클 트리는 해시의 트리로, 어떤 레코드가 데이터셋에 있음을 효율적으로 증명합니다. 인증서 투명성은 암호학적으로 검증되는 추가 전용 로그와 머클 트리로 TLS/SSL 인증서의 유효성을 검사하며, 로그마다 단일 리더를 둠으로써 합의 프로토콜을 피합니다.
§ 13.4

요약

단 하나의 도구가 모든 사용 사례를 효율적으로 처리할 수 없다는 관찰에서 시작해, 배치 처리와 이벤트 스트림으로 데이터 통합 문제를 푸는 길을 걸어왔습니다.

13.4 요약 · 통합과 언번들링

시스템 오브 레코드와, 그로부터 파생되는 모든 것

데이터 통합

어떤 시스템을 시스템 오브 레코드로 지정하고, 다른 데이터는 변환을 통해 파생시킵니다. 이렇게 인덱스, 구체화 뷰, ML 모델, 통계 요약 등을 유지할 수 있습니다.

파생과 변환을 비동기적이고 느슨하게 결합하면 한 영역의 문제가 무관한 영역으로 퍼지지 않아, 시스템 전체의 견고성과 결함 감내가 올라갑니다.

진화

데이터플로를 데이터셋 간 변환으로 표현하면 애플리케이션 진화에도 도움이 됩니다. 인덱스나 캐시 구조를 바꾸고 싶다면 전체 입력에 새 변환 코드를 다시 돌려 출력을 재파생하면 됩니다. 문제가 생기면 코드를 고쳐 재처리로 회복합니다.

언번들링

이 과정은 데이터베이스가 내부적으로 하는 일과 매우 비슷하므로, 데이터플로 애플리케이션을 데이터베이스 구성 요소의 언번들링과 느슨히 결합된 컴포넌트의 조합으로 재구성했습니다.

파생 상태는 기반 데이터의 변경을 관찰해 갱신되고, 다시 다운스트림 소비자가 관찰합니다. 이 데이터플로를 최종 사용자 기기까지 연장해, 변화를 동적으로 반영하고 오프라인에서도 동작하는 UI를 만들 수 있습니다.

13.4 요약 · 정확성

코디네이션을 피하면서도 무결성을 지키는 길

  • 강한 무결성 보장은 비동기 이벤트 처리로도 확장성 있게 구현할 수 있습니다 — 종단간 요청 식별자로 연산을 멱등하게 만들고, 제약을 비동기로 검사함으로써.
  • 클라이언트의 선택 — 검사가 통과할 때까지 기다릴 수도 있고, 기다리지 않고 진행하되 제약 위반에 대해 사과할 위험을 감수할 수도 있습니다.
  • 이 접근은 분산 트랜잭션을 쓰는 전통적 방식보다 훨씬 확장 가능하고 견고하며, 실제 많은 비즈니스 프로세스가 작동하는 방식에도 잘 맞습니다.
  • 애플리케이션을 데이터플로 중심으로 구조화하고 제약을 비동기로 검사하면 대부분의 코디네이션을 피하면서, 지리적으로 분산되고 결함이 있는 상황에서도 무결성을 유지하면서 좋은 성능을 내는 시스템을 만들 수 있습니다.
마지막으로 감사를 통해 데이터 무결성을 검증하고 손상을 탐지하는 이야기를 했고, 블록체인이 쓰는 기법이 이벤트 기반 시스템과 유사하다는 점을 관찰했습니다.
이 장 전체의 관점 — 시스템의 최고 목표는 자기 보존이 아니라 항해입니다. 배를 영원히 항구에 묶어두는 정확성이 아니라, 변화하고 진화하면서도 무결성을 지키는 정확성을 겨냥합니다.

데이터플로가
아키텍처다

모든 것을 하는 하나의 도구는 없습니다. 그렇다면 남는 질문은 "데이터를 어떻게 흐르게 할 것인가"입니다. 이벤트 로그를 축으로 시스템 오브 레코드와 파생 데이터를 나누고, 비동기·멱등·결정론이라는 세 가지 규율을 지키면 — 분산 트랜잭션 없이도 무결성을 지킬 수 있습니다.
